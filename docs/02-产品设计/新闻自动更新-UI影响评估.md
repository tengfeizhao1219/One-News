## 1. 变更概述

本次「新闻自动更新」为**纯后端数据流变更**，核心改动如下：

| 变更项 | 类型 | 说明 |
|-------|------|------|
| 新增 refreshNews 云函数 | 新增后端 | 从 GitHub raw URL 拉取 news.json 并写入云数据库 |
| 新增定时触发器 | 新增后端 | 每天 8:00 自动触发 refreshNews |
| getNewsList 缓存层级调整 | 修改后端 | 云数据库缓存从第 3 层提升到第 2 层 |
| searchNews 新增搜索层级 | 修改后端 | 新增云数据库全量拉取 + 内存过滤层 |
| 新增 news_cache 集合 | 新增后端 | 存储同步后的新闻缓存数据 |

**关键判断：前端 UI 零改动。**

所有变更发生在云函数和云数据库层，前端 `request.js` 接口签名、`home.js`/`search.js` 调用逻辑、WXML 模板、WXSS 样式均不受影响。

## 2. 现有 UI 状态影响分析

### 2.1 骨架屏（加载中状态）

| 评估维度 | 评估结果 |
|---------|---------|
| 触发条件 | 前端调用 `getNewsList`/`searchNews` → 等待云函数返回 |
| 后端变化 | getNewsList 内部缓存层级调整，但对外接口签名和返回格式不变 |
| 前端感知 | 无变化。云函数返回耗时在正常波动范围内（技术方案评估 150ms），用户体验一致 |
| 是否需要改造 | **否** |

### 2.2 错误状态

| 评估维度 | 评估结果 |
|---------|---------|
| 触发条件 | 云函数返回非 0 错误码 |
| 后端变化 | getNewsList/searchNews 增加了云数据库查询失败时的降级逻辑（降级到 AI 静态缓存或外部 API），**错误概率降低** |
| 前端感知 | 现有错误状态和重试按钮无需改动 |
| 是否需要改造 | **否** |

### 2.3 空数据状态

| 评估维度 | 评估结果 |
|---------|---------|
| 触发条件 | 所有数据源均无数据时返回空列表 |
| 后端变化 | 新增的降级链（DB 缓存 → AI 静态缓存 → 外部 API）进一步降低空数据概率 |
| 前端感知 | 现有空状态图标和文案无需改动 |
| 是否需要改造 | **否** |

### 2.4 正常数据展示状态

| 评估维度 | 评估结果 |
|---------|---------|
| 数据格式 | 云函数返回的 JSON 结构与改造前完全一致（字段名、类型、嵌套层级不变） |
| 数据内容 | 新闻内容来源从"编译期内联静态文件"变为"运行时云数据库读取"，内容更新更及时 |
| 渲染逻辑 | `formatNewsItem()`、`renderCards()` 等前端函数不受影响 |
| 是否需要改造 | **否** |

## 3. 用户体验改进

虽然无 UI 变更，但本次后端改造带来**隐性体验提升**：

### 3.1 新闻内容更新更及时

| 维度 | 改造前 | 改造后 |
|------|--------|--------|
| 更新方式 | 修改代码 → 构建 → 部署云函数（10-15 分钟） | 定时触发器自动同步（每日 8:00） |
| 更新触发 | 依赖开发者手动操作 | 全自动，PM 独立运营 |
| 用户感知 | 同一批新闻持续数天不变 | 每日打开看到当天最新新闻 |

### 3.2 数据可用性更高

| 维度 | 改造前 | 改造后 |
|------|--------|--------|
| 数据源层级 | 内存缓存 → AI 静态缓存 → DB 缓存 → 外部 API | 内存缓存 → DB 缓存(提升) → AI 静态缓存 → 外部 API |
| 故障容忍 | DB 故障时降级到静态缓存 | DB 故障时降级到静态缓存（一致） |
| 新增保护 | — | DB 为空时仍可降级到 AI 静态缓存和外部 API |

### 3.3 首次部署体验改善

| 维度 | 改造前 | 改造后 |
|------|--------|--------|
| 首次部署数据 | 依赖 `aiNewsData.js` 静态文件（需先 build） | refreshNews 首次运行后自动填充 news_cache |
| 冷启动体验 | 与改造前一致（有多层降级兜底） | 新增 DB 缓存层，数据更易热启动 |

## 4. 可选体验优化建议

以下建议不属于本次迭代范围，但可在后续迭代中考虑：

### 4.1 「上次更新时间」提示（P2）

**场景：** 用户在新闻数据同步进行中打开小程序，看到的是上一批缓存数据。

**建议：** 在首页顶部轻量展示"新闻更新于 XX:XX"，格式参考设计规范中缓存提示条的样式（顶部横幅，3 秒自动收起，可点击触发刷新）。

```
┌─────────────────────────────────┐
│ 🕐 新闻更新于 今天 08:00         │
└─────────────────────────────────┘
  背景: var(--tag-bg)
  文字: var(--text-secondary), 22rpx
```

**数据来源：** getNewsList 返回的 `meta.source` 字段已标注数据来源（`db_cache` / `ai_cache` / `external_api`），可基于此计算时间差。

### 4.2 刷新状态 toast 优化（P3）

**场景：** 用户下拉刷新时，如果恰好 refreshNews 正在执行（并发锁保护），前端无法感知后端同步进度。

**建议：** getNewsList 返回中增加 `syncStatus` 字段（`syncing` / `idle`），前端在 `syncing` 状态时展示"新闻正在更新中，请稍后刷新"的轻提示。

### 4.3 数据来源透明化（P3）

**场景：** 用户看到的新闻来自哪个数据源（DB 缓存 / AI 缓存 / 外部 API）对用户透明。

**建议：** 在"关于"或设置页展示数据来源说明，不干扰主阅读流程。
