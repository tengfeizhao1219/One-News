> 文档版本：v1.0  
> 迭代编号：Iteration 4  
> 文档类型：需求概要（Product Requirements Summary）  
> 撰写角色：产品经理  
> 撰写日期：2026-07-28

## 1. 需求背景

### 1.1 为什么要做实时新闻

一页小程序的 MVP 版本使用 18 条本地 mock 数据来展示新闻卡片流，这在初期验证产品形态和交互体验时是合理的策略。但随着产品进入下一阶段，mock 数据已成为制约产品价值的核心瓶颈。

**WHEN** 用户打开一页小程序浏览新闻  
**IF** 所有内容均为写死的 mock 数据  
**THEN** 用户刷到重复内容后失去信任，**THE SYSTEM SHALL** 提供来自真实新闻源的实时数据，保证新闻内容的时效性和多样性。

具体驱动因素：

| 驱动因素 | 说明 |
|---------|------|
| 产品价值 | 新闻阅读类产品的核心价值在于"新"，mock 数据无法体现这一属性 |
| 用户留存 | 18 条固定内容无法支撑用户的持续刷屏行为，导致次日留存率低下 |
| 内容厚度 | 5 个分类共 18 条数据，单个分类仅 3-4 条，用户 2-3 屏即刷完 |
| 迭代准备 | 后续计划引入个性化推荐、热点追踪等功能，依赖真实数据作为输入 |

### 1.2 目标

将一页小程序从"静态 Demo"升级为"实时新闻阅读器"，实现：
- 接入至少一个稳定新闻数据源
- 每个分类提供持续更新的新闻内容
- 保证新闻数据的时效性（最新新闻在 1 小时内可被拉取到）
- 保持现有卡片流 UI 交互体验不变

## 2. 现状分析

### 2.1 当前 Mock 数据问题

#### 2.1.1 时效性为零

| 指标 | 当前值 | 期望值 |
|-----|--------|--------|
| 数据更新频率 | 从不更新 | 实时/准实时 |
| 最新新闻时间 | 写死为 `Date.now() - N小时`（每次重启重置） | 真实发布时间 |
| 内容新鲜度 | 用户每次打开都是同样的 18 条 | 每次打开都有新内容 |

**核心问题**：mock 数据中的 `time` 字段使用 `new Date(Date.now() - N * 3600000)` 动态计算，虽然从代码角度看起来"在更新"，但新闻标题、摘要、正文内容从未变化。用户在第二次打开小程序时就会发现所有内容都已读过。

#### 2.1.2 数据量严重不足

```
总数据量：18 条
├── 推荐：3 条
├── 科技：4 条
├── 国际：3 条（分类 ID 为 international，但常量中无此分类）
├── 体育：3 条
└── 生活：4 条
```

- 单次分页 `PAGE_SIZE = 10`，用户一屏即刷完全部分类的 70% 内容
- 搜索功能在 18 条数据中匹配，几乎无实用价值
- 无法支撑"无限刷"的抖音式交互体验

#### 2.1.3 数据分类不匹配

| Mock 数据中的分类 | constants.js 中的分类 | 状态 |
|------------------|----------------------|------|
| `recommend` | `recommend` | 匹配 |
| `tech` | `tech` | 匹配 |
| `international` | **不存在** | 不匹配 |
| `sports` | `sports` | 匹配 |
| `life` | `life` | 匹配 |

constants.js 定义的 5 个分类为：`all`、`recommend`、`tech`、`sports`、`life`。但 mock 数据中包含 `international` 分类的 3 条数据，这些数据在通过 `getNewsListMock` 按分类筛选时会被过滤掉（因为 `CATEGORY_MAP` 中没有 `international` 键），导致实际可用的数据只有 15 条。

#### 2.1.4 内容真实性问题

- 所有新闻为虚构内容，包含虚构的引用、数据、机构名称
- 无法作为真实信息消费，降低了产品的可信度
- 无法接入后续计划的内容审核、舆情分析等模块

### 2.2 当前架构概览

```
┌──────────────────────────────────────────────┐
│                  小程序前端                     │
│  home.js → request.js → getNewsList()         │
│                              ↓                │
│                    USE_MOCK ?                  │
│                    /        \                  │
│              Mock 模式    云函数模式             │
│              (直接返回     (wx.cloud            │
│               mock/news)   .callFunction)      │
│                              ↓                │
│                      云函数 getNewsList         │
│                      云函数 searchNews          │
│                      (查询云数据库 news 集合)     │
└──────────────────────────────────────────────┘
```

关键发现：
- `request.js` 已内置 mock/cloud 双模式切换机制（`USE_MOCK` 常量控制）
- 云函数 `getNewsList` 和 `searchNews` 已实现对云数据库 `news` 集合的查询
- 当前 `USE_MOCK = false`（生产模式），但云数据库中实际没有数据
- `formatNewsItem()` 统一了 mock 和 cloud 两种来源的数据格式

## 3. 用户故事

### US-01：普通用户刷到新鲜新闻

> **作为** 一个日常通勤用户  
> **我希望** 每次打开一页小程序都能看到当天最新的新闻  
> **以便** 我可以在碎片时间快速了解时事热点  

**EARS 验收条件**：

- **WHEN** 用户首次打开小程序或下拉刷新  
- **IF** 网络连接正常  
- **THEN THE SYSTEM SHALL** 在 3 秒内向用户展示最近 24 小时内发布的新闻列表
- **WHEN** 用户持续下滑刷屏  
- **IF** 仍有更多新闻可加载  
- **THEN THE SYSTEM SHALL** 自动加载下一页数据，每次加载 10 条

### US-02：分类阅读者切换频道看新闻

> **作为** 一个偏好科技新闻的用户  
> **我希望** 切换到"科技"分类后看到该领域的最新新闻  
> **以便** 我可以专注于自己感兴趣的领域  

**EARS 验收条件**：

- **WHEN** 用户通过侧边栏切换到某一分类（如"科技"）  
- **IF** 该分类下有可用数据  
- **THEN THE SYSTEM SHALL** 仅展示该分类下的新闻，按发布时间倒序排列
- **WHEN** 用户切换到的分类暂无数据  
- **IF** 网络请求返回空列表  
- **THEN THE SYSTEM SHALL** 展示空状态提示"暂无新闻，下拉刷新试试"

### US-03：搜索用户查找特定新闻

> **作为** 一个对特定话题感兴趣的用户  
> **我希望** 通过关键词搜索找到相关新闻  
> **以便** 我可以快速定位关注的信息  

**EARS 验收条件**：

- **WHEN** 用户在搜索框输入关键词并提交  
- **IF** 存在标题或摘要匹配的新闻  
- **THEN THE SYSTEM SHALL** 返回相关新闻列表，按发布时间倒序
- **WHEN** 搜索结果为空  
- **IF** 无任何新闻匹配关键词  
- **THEN THE SYSTEM SHALL** 展示"未找到相关新闻"提示

### US-04：弱网用户的基本可用性

> **作为** 一个在地铁/电梯等弱网环境下的用户  
> **我希望** 在加载失败时能看到友好的提示  
> **以便** 我知道发生了什么，并可以重试  

**EARS 验收条件**：

- **WHEN** 新闻数据请求因网络原因失败  
- **IF** 请求超时（超过 10 秒）或返回错误  
- **THEN THE SYSTEM SHALL** 展示"网络开小差了，请重试"提示，并提供重试按钮
- **WHEN** 用户点击重试  
- **IF** 网络恢复  
- **THEN THE SYSTEM SHALL** 重新发起请求并正常展示数据

## 5. 新闻源方案建议

### 5.1 方案对比

| 维度 | 方案 A：免费新闻 API 聚合 | 方案 B：自建爬虫 | 方案 C：RSS 订阅聚合 |
|-----|------------------------|-----------------|---------------------|
| **实现复杂度** | 低 — 调用 RESTful API 即可 | 高 — 需开发爬虫、反爬、清洗、存储 | 中 — 解析 RSS/Atom 标准格式 |
| **维护成本** | 低 — API 服务商维护 | 极高 — 目标网站改版即失效 | 中 — RSS 源可能停更或变更 |
| **数据时效性** | 高 — 通常 5-30 分钟延迟 | 最高 — 可做到分钟级 | 中 — 依赖源站更新频率 |
| **数据质量** | 高 — 服务商已做清洗 | 不稳定 — 需自行清洗 | 中 — 格式规范但内容参差 |
| **版权风险** | 低 — API 服务商已获得授权 | 高 — 存在侵权风险 | 中 — RSS 为网站主动提供 |
| **费用** | 免费额度有限，大规模需付费 | 服务器 + 代理 IP 成本 | 几乎免费 |
| **内容覆盖** | 取决于服务商支持范围 | 可定制 | 取决于 RSS 源数量 |
| **合规性** | 高 | 低（灰色地带） | 中 |
| **扩展性** | 取决于 API 配额 | 灵活 | 受限于 RSS 源数量 |
| **微信小程序兼容** | 好 — 标准 HTTPS API | 需中间服务器转发 | 需中间服务器转发 |

### 5.2 推荐方案

**推荐方案 A：免费新闻 API 聚合**，理由如下：

1. **合规优先**：微信小程序对内容合规要求严格，API 服务商已解决版权问题
2. **快速上线**：从 mock 切换到 API 调用，仅需修改云函数的数据获取逻辑，预计 2-3 天可完成
3. **低风险**：无需处理反爬、IP 封禁、HTML 解析等爬虫常见问题
4. **可渐进演进**：先用免费 API 验证数据链路，后续可按需升级付费方案或自建数据源

### 5.3 候选 API 服务商

| 服务商 | 免费额度 | 特点 |
|-------|---------|------|
| 聚合数据 | 100 次/天 | 国内新闻源丰富，中文支持好 |
| 天行数据 | 100 次/天 | 分类齐全，适合小程序 |
| NewsAPI | 100 次/天 | 国际新闻为主，英文 |
| 网易/头条开放平台 | 视合作情况 | 数据量大，但接入门槛较高 |

**建议**：优先对接天行数据或聚合数据的新闻 API，评估数据质量后再决定是否扩展。

### 5.4 架构方案

```
┌──────────────────────────────────────────────────────┐
│                     小程序前端                         │
│  request.js → wx.cloud.callFunction('getNewsList')    │
└────────────────────────┬─────────────────────────────┘
                         │
┌────────────────────────▼─────────────────────────────┐
│              云函数 getNewsList（改造后）                │
│  1. 接收前端请求 (category, pageNum, pageSize)          │
│  2. 映射分类 ID 到 API 分类参数                          │
│  3. 调用外部新闻 API                                    │
│  4. 将 API 返回数据映射为前端格式                         │
│  5. 返回统一结构的新闻列表                               │
└────────────────────────┬─────────────────────────────┘
                         │
┌────────────────────────▼─────────────────────────────┐
│              外部新闻 API（天行/聚合等）                  │
│  - GET /news/list?category=tech&page=1&size=10        │
│  - 返回 JSON：{ code, msg, data: { list, total } }     │
└──────────────────────────────────────────────────────┘
```

云函数作为中间层的优势：
- API Key 存储在云函数环境变量中，不暴露给前端
- 可以缓存热点数据，减少 API 调用次数
- 统一数据格式转换，前端无需感知 API 差异
- 未来切换 API 服务商只需改云函数，前端无感知

## 6. 关键边界场景

### 6.1 网络异常

| 场景 | 触发条件 | 系统行为 |
|-----|---------|---------|
| 请求超时 | API 响应时间 > 10s | 提示"网络开小差了"，提供重试按钮 |
| DNS 解析失败 | 无网络连接 | 提示"当前无网络连接，请检查网络设置" |
| API 服务不可用 | HTTP 5xx 错误 | 提示"新闻服务暂时不可用，请稍后重试"，自动记录错误日志 |
| 首次加载失败 | 用户首次打开且请求失败 | 展示空状态页 + 重试按钮（不展示 mock 数据） |

### 6.2 API 限流

| 场景 | 触发条件 | 系统行为 |
|-----|---------|---------|
| 日配额耗尽 | 免费额度用尽（如 100 次/天） | 提示"今日阅读次数已用完，明天再来吧" |
| 频率限制 | 短时间内频繁请求 | 前端增加防抖（1 秒内不重复请求同一分类） |
| 降级策略 | API 连续失败 3 次 | 云函数缓存最近一次成功数据作为兜底 |

### 6.3 数据为空

| 场景 | 触发条件 | 系统行为 |
|-----|---------|---------|
| 分类无数据 | API 返回该分类空列表 | 展示空状态"暂无新闻，下拉刷新试试" |
| 搜索无结果 | 关键词无匹配 | 展示空状态"未找到相关新闻，换个关键词试试" |
| 全部无数据 | 所有分类均返回空 | 检查 API 是否正常，展示"暂无新闻" |

### 6.4 数据格式不兼容

| 场景 | 触发条件 | 系统行为 |
|-----|---------|---------|
| 字段缺失 | API 返回数据缺少 title/summary 等关键字段 | 跳过该条数据，记录日志，继续展示其他数据 |
| 类型错误 | publishTime 为字符串而非时间戳 | 适配器层做类型转换，无法转换的跳过 |
| 编码问题 | 中文乱码 | 适配器层做 UTF-8 解码，失败的跳过 |
| 字段值异常 | title 为空字符串或 null | 使用默认文案"[无标题]" |
| 图片字段变化 | API 无 image 字段或字段名不同 | 使用默认占位图，不阻断列表展示 |

### 6.5 分页边界

| 场景 | 触发条件 | 系统行为 |
|-----|---------|---------|
| 已加载全部 | hasMore = false | 底部展示"已经到底了" |
| 翻页过程中切换分类 | 用户在加载中切换分类 | 取消前一个请求，发起新分类请求 |
| 并发翻页 | 用户快速下滑触发多次加载 | 前端加锁，上一页未加载完成时不触发下一页 |

## 7. 数据字段映射

### 7.1 前端数据模型（目标格式）

```javascript
// request.js formatNewsItem() 输出格式
{
  id:          String,    // 新闻唯一标识
  _id:         String,    // 兼容云数据库 _id 字段
  title:       String,    // 新闻标题
  summary:     String,    // 新闻摘要
  content:     String?,   // 新闻正文（仅详情接口返回）
  category:    String,    // 分类 ID
  categoryName:String,    // 分类中文名
  source:      String,    // 新闻来源
  time:        String,    // 相对时间（如"3小时前"）
  publishTime: String|Number  // 发布时间（原始值）
}
```

### 7.2 Mock 数据字段 → 通用 API 字段映射

| 前端字段 | Mock 字段 | 通用 API 字段（预期） | 类型 | 映射说明 |
|---------|----------|---------------------|------|---------|
| `id` | `id` (如 `'r001'`) | `news_id` / `uniquekey` | String | API 通常返回数字 ID 或 UUID |
| `_id` | 同 `id` | 同 `id` | String | 保持与 id 一致 |
| `title` | `title` | `title` | String | 直接映射 |
| `summary` | `summary` | `description` / `digest` | String | API 可能使用不同字段名 |
| `content` | `content` | `content` | String | 详情接口返回 |
| `category` | `category` (如 `'tech'`) | `category` / `channel` | String | 需要做枚举映射 |
| `categoryName` | `categoryName` (如 `'科技'`) | `category_name` | String | 需要做枚举映射 |
| `source` | `source` (如 `'科技日报'`) | `source` / `author_name` | String | 直接映射 |
| `publishTime` | `time` (Date 对象) | `pub_time` / `date` | String/Number | 需统一转为 ISO 字符串或时间戳 |
| `time` | 由 `formatRelativeTime()` 计算 | 同上 | String | 前端统一格式化，不依赖 API |

### 7.3 分类枚举映射

由于外部 API 的分类体系与一页的分类体系不一致，需要在云函数中维护一个分类映射表：

```javascript
// 一页分类 → API 分类的映射（示例，需根据实际 API 调整）
const CATEGORY_MAPPING = {
  'recommend':     'top',        // 推荐 → 头条/综合
  'tech':          'tech',       // 科技
  'sports':        'sports',     // 体育
  'life':          'life',       // 生活
  'all':           null          // 全部 → 不传分类参数
}

// API 分类 → 一页分类的反向映射
const REVERSE_CATEGORY_MAPPING = {
  'top':           'recommend',
  'tech':          'tech',
  'sports':        'sports',
  'life':          'life',
  'finance':       'recommend',  // API 有但一页没有的分类，归入推荐
  'entertainment': 'life'        // 同上
}
```

### 7.4 数据适配器设计

```javascript
/**
 * 将外部 API 返回的新闻数据映射为前端统一格式
 * @param {Object} apiItem - API 返回的单条新闻
 * @returns {Object} 前端格式的新闻对象
 */
function adaptNewsItem(apiItem) {
  const id = String(apiItem.uniquekey || apiItem.news_id || '')
  return {
    id,
    _id: id,
    title: apiItem.title || '[无标题]',
    summary: apiItem.description || apiItem.digest || '',
    category: REVERSE_CATEGORY_MAPPING[apiItem.category] || 'recommend',
    categoryName: CATEGORY_MAP[REVERSE_CATEGORY_MAPPING[apiItem.category]] || '推荐',
    source: apiItem.source || apiItem.author_name || '未知来源',
    publishTime: apiItem.date || apiItem.pub_time || new Date().toISOString()
  }
}
```

| 编号 | 风险描述 | 影响 | 概率 | 应对措施 |

| R1 | **API 服务商停止服务或变更接口** | 高 — 新闻无法获取 | 中 | 云函数做适配层，切换 API 只需改云函数；保留至少一个备用 API |
| R2 | **免费 API 配额不足** | 高 — 高峰期用户无法加载新闻 | 高 | 1) 云函数做结果缓存（5-10 分钟 TTL）2) 前端做请求防抖 3) 准备付费升级预算 |
| R3 | **API 返回数据包含违规内容** | 极高 — 小程序被下架 | 中 | 云函数做关键词过滤，过滤敏感词；接入微信内容安全 API |
| R4 | **API 数据格式与预期不符** | 中 — 部分新闻无法展示 | 高 | 适配器做防御性解析，字段缺失时使用默认值而非崩溃 |
| R5 | **分类体系不匹配** | 中 — 分类筛选不准确 | 高 | 维护分类映射表，定期检查分类覆盖率 |
| R6 | **冷启动无数据** | 中 — 首次部署无历史数据 | 中 | 云函数首次调用时拉取多页数据（如 5 页）填充缓存 |
| R7 | **API 响应时间过长影响用户体验** | 中 — 白屏等待 | 中 | 设置 10s 超时，超时后展示友好错误提示；云函数加缓存减少重复请求 |
| R8 | **微信小程序服务器域名白名单限制** | 高 — 请求被拦截 | 低 | 通过云函数中转请求，无需配置 request 合法域名 |
| R9 | **现有 `international` 分类数据处理** | 低 — 3 条 mock 数据不可见 | 低 | 评估是否需要新增"国际"分类，或将其归入"推荐" |

## 附录 A：EARS 原则说明

本文档中的需求描述遵循 EARS（Easy Approach to Requirements Syntax）原则，采用以下句式模板：

| 类型 | 模板 | 用途 |
|-----|------|------|
| Ubiquitous | **THE SYSTEM SHALL** `<行为>` | 描述始终成立的需求 |
| Event-driven | **WHEN** `<触发条件>` **THE SYSTEM SHALL** `<行为>` | 描述由事件触发的需求 |
| Unwanted behavior | **IF** `<异常条件>` **THEN THE SYSTEM SHALL** `<行为>` | 描述异常处理需求 |
| State-driven | **WHILE** `<状态>` **THE SYSTEM SHALL** `<行为>` | 描述状态持续期间的需求 |
| Optional | **WHERE** `<特征>` **THE SYSTEM SHALL** `<行为>` | 描述特定条件下的需求 |
