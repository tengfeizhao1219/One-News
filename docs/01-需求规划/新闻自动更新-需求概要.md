> 文档类型：需求概要（Product Requirements Summary）  
> 撰写角色：产品经理

## 1. 需求背景

### 1.1 为什么要做新闻自动更新

当前一页小程序的新闻内容来源于 WorkBuddy AI 搜索生成的 JSON 缓存（`mock/ai-news-cache.js`），通过 build 脚本转换为云函数数据文件（`cloudfunctions/common/aiNewsData.js`），随代码一起部署到 CloudBase。

这个流程保证了初始阶段内容可配、可版本管理，但随着产品进入常态化运营阶段，其弊端日益凸显。

**WHEN** 产品需要更新新闻内容  
**IF** 每次更新都依赖"修改缓存 → 构建 → 重新部署云函数"的完整链路  
**THEN** 内容更新周期被拉长至小时级甚至天级，**THE SYSTEM SHALL** 实现新闻内容的自动化更新，使内容与代码解耦，无需部署即可刷新新闻。

具体驱动因素：

| 驱动因素 | 说明 |
|---------|------|
| 运营效率 | 当前流程需要开发者全程参与，PM 无法自主更新内容，运营成本高 |
| 内容时效性 | "修改代码 → 构建 → 部署"链路最少耗时 10-15 分钟，无法支撑新闻产品对时效性的基本要求 |
| 运维成本 | 每次新闻更新都是一次完整部署，消耗 CI/CD 资源和部署配额 |
| 架构合理性 | 内容数据与业务代码耦合在同一个部署单元中，违反关注点分离原则 |
| 自动化能力 | 当前流程完全依赖人工触发，无法实现定时自动更新，无法做到"每天自动推送新内容" |

### 1.2 目标

将新闻内容更新从"人工触发 + 代码部署"模式升级为"AI 生成 + Git 触发 + 定时同步"模式，实现：

- 新闻内容与业务代码完全解耦
- 新闻每天自动更新一次，无需人工介入
- 更新链路不依赖云函数重新部署
- 小程序前端数据获取逻辑平滑迁移至云数据库读取
- 保持现有卡片流 UI 交互体验不变

## 2. 现状分析

### 2.1 当前内容更新链路（痛点）

```
WorkBuddy AI 搜索新闻
    ↓
生成 mock/ai-news-cache.js（JavaScript 模块格式）
    ↓
执行 build 脚本（npm run build:news）
    ↓
转换为 cloudfunctions/common/aiNewsData.js
    ↓
随云函数代码一起部署（tcb deploy）
    ↓
小程序调用 getNewsList → 云函数读取 aiNewsData.js → 返回
```

**核心痛点总结**：

| 痛点 | 描述 | 影响 |
|-----|------|------|
| 内容与代码耦合 | 新闻数据内嵌在云函数代码中 | 更新内容必须重新部署云函数 |
| 更新链路长 | 修改 → 构建 → 部署，至少 3 步 | 单次更新时间 10-15 分钟 |
| 依赖开发者 | PM 无法独立完成内容更新 | 运营效率低下 |
| 无法自动化 | 缺少定时触发机制 | 无法实现"每天自动更新" |
| 部署成本高 | 每次更新消耗 CloudBase 部署配额 | 频繁更新不可持续 |

## 3. 用户故事

### US-01：PM 自主更新新闻内容

> **作为** 一位产品经理  
> **我希望** 通过 WorkBuddy 生成新闻内容后，无需联系开发者即可完成内容发布  
> **以便** 我可以独立运营新闻内容，提升更新效率

**EARS 验收条件**：

- **WHEN** PM 通过 WorkBuddy 生成新闻内容  
- **IF** 生成的 `data/news.json` 被推送到 GitHub 仓库  
- **THEN THE SYSTEM SHALL** 在下一个定时周期（每天）自动将新内容同步到云数据库，无需任何人工干预
- **WHEN** PM 紧急更新新闻内容（非定时周期内）  
- **IF** 需要立即生效  
- **THEN THE SYSTEM SHALL** 支持手动触发 refreshNews 云函数以立即同步

### US-02：普通用户每天看到新鲜新闻

> **作为** 一个日常使用一页小程序的用户  
> **我希望** 每天打开小程序都能看到当天最新的新闻  
> **以便** 我可以持续消费新鲜内容，保持使用习惯

**EARS 验收条件**：

- **WHEN** 用户每天首次打开小程序  
- **IF** refreshNews 已成功执行当日同步  
- **THEN THE SYSTEM SHALL** 展示当日更新的新闻列表，内容不同于前一天
- **WHEN** 新闻数据正在同步过程中  
- **IF** 用户打开小程序请求新闻  
- **THEN THE SYSTEM SHALL** 返回上一批次缓存的新闻数据，不展示空列表

### US-03：开发者免于内容运维

> **作为** 一位开发者  
> **我希望** 新闻内容更新不再依赖代码部署流程  
> **以便** 我可以专注于功能开发和系统稳定性，不被内容运维打断

**EARS 验收条件**：

- **WHEN** 新闻内容需要更新  
- **IF** 新的 `data/news.json` 已存在于 GitHub 仓库  
- **THEN THE SYSTEM SHALL** 自动完成同步，**无需**开发者执行任何部署操作
- **WHEN** 定时触发或手动触发 refreshNews 执行失败  
- **IF** 失败原因为网络超时或数据格式错误  
- **THEN THE SYSTEM SHALL** 记录错误日志并通过企业微信/邮件通知开发者

### 5.1 数据流全景

```
┌──────────────────────────────────────────────────────┐
│                    WorkBuddy AI                        │
│  搜索新闻 → 生成 data/news.json（纯 JSON 格式）           │
└────────────────────────┬─────────────────────────────┘
                         │ git push
┌────────────────────────▼─────────────────────────────┐
│                  GitHub 仓库                           │
│  data/news.json                                       │
│  可通过 Raw URL 访问：                                  │
│  https://raw.githubusercontent.com/.../data/news.json │
└────────────────────────┬─────────────────────────────┘
                         │ HTTP GET（Raw URL）
┌────────────────────────▼─────────────────────────────┐
│         CloudBase 定时触发器（每天 06:00）               │

                         │ 写入

│         云数据库 news_cache 集合                         │

│  ├── categoryName: 分类中文名                           │
│  ├── source: 来源                                      │

│  ├── imageUrl: 图片 URL                                │

                         │ 查询
┌────────────────────────▼─────────────────────────────┐
│              getNewsList / searchNews 云函数             │
```

### 5.2 news.json 数据格式规范

```json
{
  "version": "1.0",
  "generatedAt": "2026-07-28T06:00:00Z",
  "totalCount": 50,
  "news": [
    {
      "newsId": "n001",
      "title": "新闻标题",
      "summary": "新闻摘要，控制在 200 字以内",
      "content": "新闻正文，支持 Markdown 格式",
      "category": "tech",
      "categoryName": "科技",
      "source": "来源媒体名称",
      "publishTime": "2026-07-28T08:00:00Z",
      "imageUrl": "https://example.com/image.jpg"
    }
  ]
}
```

### 5.3 云数据库索引设计

| 索引名称 | 字段 | 方向 | 用途 |
|---------|------|------|------|
| `idx_category_publishTime` | `category` + `publishTime` | 升序 + 降序 | getNewsList 按分类分页查询 |
| `idx_newsId` | `newsId` | 升序 | 去重和单条查询 |
| `idx_syncTime` | `syncTime` | 降序 | 查询最近同步记录 |

### 5.4 refreshNews 云函数核心逻辑

```javascript
// refreshNews/index.js 伪代码
exports.main = async (event, context) => {
  const GITHUB_RAW_URL = 'https://raw.githubusercontent.com/{owner}/{repo}/main/data/news.json'
  
  try {
    // 1. 从 GitHub 拉取最新 news.json
    const response = await fetch(GITHUB_RAW_URL)
    if (!response.ok) throw new Error(`HTTP ${response.status}`)
    
    const data = await response.json()
    
    // 2. 数据校验
    if (!data.news || !Array.isArray(data.news)) {
      throw new Error('Invalid news.json format: missing news array')
    }
    
    // 3. 字段映射 & 补充元数据
    const now = Date.now()
    const documents = data.news.map(item => ({
      newsId: item.newsId,
      title: item.title || '[无标题]',
      summary: item.summary || '',
      content: item.content || '',
      category: item.category || 'recommend',
      categoryName: item.categoryName || '推荐',
      source: item.source || '未知来源',
      publishTime: item.publishTime || new Date().toISOString(),
      imageUrl: item.imageUrl || '',
      syncTime: now
    }))
    
    // 4. 先删后写（事务性替换）
    const db = cloud.database()
    const collection = db.collection('news_cache')
    
    // 分批删除旧数据（云数据库单次 delete 有限制）
    await batchDelete(collection)
    
    // 分批写入新数据（云数据库单次 add 有限制）
    await batchInsert(collection, documents)
    
    // 5. 记录同步日志
    await db.collection('sync_logs').add({
      data: {
        syncTime: now,
        newsCount: documents.length,
        status: 'success',
        sourceVersion: data.version
      }
    })
    
    return { code: 0, msg: 'success', count: documents.length }
    
  } catch (error) {
    // 记录失败日志
    await logError(error)
    return { code: -1, msg: error.message }
  }
}
```

## 6. 关键边界场景

### 6.1 GitHub Raw URL 访问异常

| 场景 | 触发条件 | 系统行为 |
|-----|---------|---------|
| GitHub 不可达 | DNS 解析失败或网络不通 | 记录错误日志，保留上一批缓存数据不变，下次定时重试 |
| Raw URL 返回 404 | 仓库路径变更或文件不存在 | 记录错误日志，通知开发者检查 Raw URL 配置 |
| 响应超时 | 请求超过 30 秒无响应 | 重试 1 次，仍失败则记录日志并放弃本次同步 |
| 响应内容非 JSON | GitHub 返回 HTML 错误页 | 解析失败，记录日志，保留旧数据 |

### 6.2 数据格式异常

| 场景 | 触发条件 | 系统行为 |
|-----|---------|---------|
| JSON 解析失败 | 文件格式损坏 | 终止同步，记录错误日志，保留旧数据 |
| news 字段为空数组 | 生成失败或数据源无内容 | 跳过本次同步，保留旧数据，记录警告日志 |
| 部分字段缺失 | 单条新闻缺少 title/category 等 | 使用默认值填充（如 `[无标题]`），继续同步其他数据 |
| newsId 重复 | news.json 中存在重复 ID | 去重处理，保留首次出现的记录 |
| 数据量过大 | news.json 超过 5MB | 分页写入，单次写入不超过 100 条 |

### 6.3 云数据库操作异常

| 场景 | 触发条件 | 系统行为 |
|-----|---------|---------|
| 写入超时 | 数据量大导致写入耗时过长 | 分批写入（每批 50 条），单批超时重试 |
| 配额耗尽 | 云数据库写入次数超限 | 记录错误日志，通知开发者升级配额 |
| 并发写入冲突 | 手动触发和定时触发同时执行 | 云函数加互斥锁，同一时间只允许一个同步任务执行 |

### 6.4 同步过程中的数据可用性

| 场景 | 触发条件 | 系统行为 |
|-----|---------|---------|
| 同步进行中 | 用户请求新闻时 refreshNews 正在执行 | getNewsList 返回同步前的旧数据，不受同步过程影响 |
| 首次部署无数据 | news_cache 集合为空 | getNewsList 返回空列表 + "暂无新闻，请稍后再来"提示 |
| 同步中断 | 部分数据写入成功后被中断 | 由于采用"先删后写"策略，可能短暂出现数据不完整；优化方案为"先写新数据，再删旧数据" |

|-----|---------|------|------|---------|
| R1 | **GitHub Raw URL 不可达**（网络限制/GitHub 服务异常） | 高 — 新闻无法同步 | 低 | 配置备用 Raw URL（如 Gitee 镜像）；refreshNews 失败保留旧数据不覆盖 |
| R2 | **云数据库写入配额不足** | 高 — 数据无法写入 | 中 | 分批写入降低单次消耗；监控配额使用情况，提前预警 |
| R3 | **news.json 数据格式变更导致解析失败** | 高 — 同步中断 | 中 | 定义明确的数据格式规范（JSON Schema）；refreshNews 做防御性解析 |
| R4 | **定时触发器执行失败无感知** | 中 — 新闻长期不更新 | 中 | 每次执行记录 sync_logs；失败时通过企业微信/邮件告警 |
| R5 | **getNewsList/searchNews 改造引入查询性能问题** | 中 — 用户加载变慢 | 低 | 建立数据库索引；云函数查询使用分页限制单次返回量 |
| R6 | **GitHub 仓库权限变更导致无法访问** | 高 — 同步中断 | 低 | 使用公开仓库或配置 Personal Access Token |
| R7 | **先删后写策略导致短暂数据不可用** | 中 — 同步期间用户看到空列表 | 中 | 优化为"先写后删"策略，或在删除前先查询确认新数据已写入 |
| R8 | **WorkBuddy 生成的 news.json 包含违规内容** | 极高 — 小程序被下架 | 低 | refreshNews 同步前接入微信内容安全 API 做内容审核；人工抽检 |

## 9. 验收标准

### 9.1 功能验收

| 编号 | 验收项 | 验收方法 |
|-----|-------|---------|
| AC1 | **WHEN** 定时触发器到达设定时间 **THEN THE SYSTEM SHALL** 自动执行 refreshNews，将 `news.json` 内容同步到云数据库 `news_cache` 集合 | 查看 CloudBase 云函数调用日志，确认 refreshNews 被执行且返回成功 |
| AC2 | **WHEN** PM 通过 WorkBuddy 生成新内容并 push 到 GitHub **THEN THE SYSTEM SHALL** 在下一次定时触发时自动更新数据 | 修改 `data/news.json` 内容，等待下次定时执行后验证云数据库数据已更新 |
| AC3 | **WHEN** PM 手动调用 refreshNews **IF** GitHub Raw URL 可访问 **THEN THE SYSTEM SHALL** 立即同步最新数据 | 在 CloudBase 控制台手动触发 refreshNews，验证数据更新 |
| AC4 | **WHEN** getNewsList 云函数被调用 **IF** `news_cache` 中有数据 **THEN THE SYSTEM SHALL** 从云数据库查询并返回新闻列表 | 调用 getNewsList，验证返回数据与 `news_cache` 集合一致 |
| AC5 | **WHEN** searchNews 云函数被调用 **IF** 关键词匹配到新闻 **THEN THE SYSTEM SHALL** 从云数据库查询并返回匹配结果 | 调用 searchNews，验证搜索结果正确 |
| AC6 | **WHEN** refreshNews 执行失败 **IF** GitHub 不可达或数据格式错误 **THEN THE SYSTEM SHALL** 记录错误日志到 `sync_logs`，保留旧数据不变 | 模拟 GitHub 不可达，验证旧数据未被清除且日志已记录 |
| AC7 | **WHEN** `news_cache` 集合为空（首次部署） **IF** 用户请求新闻 **THEN THE SYSTEM SHALL** 返回空列表并展示"暂无新闻"提示 | 清空 news_cache 后测试 |

## 附录 A：EARS 原则说明

本文档中的需求描述遵循 EARS（Easy Approach to Requirements Syntax）原则，采用以下句式模板：

| 类型 | 模板 | 用途 |
|-----|------|------|
| Ubiquitous | **THE SYSTEM SHALL** `<行为>` | 描述始终成立的需求 |
| Event-driven | **WHEN** `<触发条件>` **THE SYSTEM SHALL** `<行为>` | 描述由事件触发的需求 |
| Unwanted behavior | **IF** `<异常条件>` **THEN THE SYSTEM SHALL** `<行为>` | 描述异常处理需求 |
| State-driven | **WHILE** `<状态>` **THE SYSTEM SHALL** `<行为>` | 描述状态持续期间的需求 |
| Optional | **WHERE** `<特征>` **THE SYSTEM SHALL** `<行为>` | 描述特定条件下的需求 |

## 附录 C：与"实时新闻"需求的关系

本需求（新闻自动更新）是 Iteration 4 "实时新闻"需求的基础设施层改造。两者的关系如下：

| 维度 | 实时新闻需求 | 新闻自动更新需求 |
|-----|------------|----------------|
| 关注点 | 内容来源：从 mock 到真实新闻 | 更新机制：从手动部署到自动同步 |
| 数据流向 | 外部 API → 云函数 → 前端 | WorkBuddy → GitHub → refreshNews → 云数据库 → 云函数 → 前端 |
| 依赖关系 | 依赖新闻自动更新提供稳定的数据管道 | 为实时新闻需求提供数据基础设施 |
| 优先级 | P0 | P0（先于实时新闻上线） |

建议上线顺序：先完成新闻自动更新（本需求），确保数据管道通畅后，再接入真实新闻 API 替换 WorkBuddy 内容源。
