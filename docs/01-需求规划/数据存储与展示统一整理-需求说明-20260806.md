## 一、背景与目标

owner 指出当前**数据存储与展示口径混乱**，核心矛盾：

1. 首页列表、侧边栏、详情页各自维护「一套新闻」，数量/顺序/范围不一致；
2. 「过期新闻」的可见性与可读性规则不明确；
3. 从浏览历史/收藏进入详情后，滑动范围与来源列表无关；
4. 首页翻底/翻顶的拉取行为与提示文案不统一。

**目标**：统一「一套数据、一套顺序、一套边界」，让用户在任何入口阅读时，滑动范围都清晰、可预期。

## 三、目标规则（统一数据口径）

### R1 一套数据源
> 首页卡片流、侧边栏、详情页**必须同源**：均以首页当前分类的 `newsList`（含分页追加）为唯一事实源。

- 侧边栏：`filteredNewsList` 继续由 `newsList` 派生（现状已满足，保持）。
- 详情页：进入时接收完整 `newsList`（含已追加分页），**滑动范围 = 该列表**，禁止跨分类补拉。

### R2 过期即隐形（列表）· 留存即可读（详情）
> 「过期」= `cacheExpire` 已过（普通 7 天 / retained 30 天）。

- **列表/侧边栏**：只展示未过期新闻，**禁用 stale 兜底混入过期**（见待确认项 ①）。
- **详情**：未过期 + retained（收藏/分享/浏览历史留存）新闻可读；未读且已过期 → 「新闻不存在或已过期」。

### R3 阅读范围 = 来源列表
> 从首页进入：滑动范围 = 当前分类 `newsList`（含分页）；从历史/收藏进入：滑动范围 = 来源列表顺序。

### R4 边界必有反馈
> 任何入口的「第一条上滑/最后一条上滑」都必须有 toast，禁止静默。

### R5 拉取有节奏
> 首页翻底/翻顶统一 toast「抓取更多新闻中」，后台拉**当前所属分类 5 条**；连续拉取满 3 次（15 条）后提示「已阅读了 x 条新闻，建议稍后再读」。

## 四、分项方案

### 方案 1：侧边栏/列表过期过滤（owner 点 1）

**改动**：`getNewsList` 禁用 stale 兜底（删除 `index.js:33-46` 放宽逻辑），列表与侧边栏天然只含未过期新闻。
**兜底**：fresh 为空时返回空列表 → 前端显示空态「暂无新闻，下拉刷新」；refreshNews 每小时自动补抓。
**风险**：极端情况（外部 API 故障且缓存全过期）可能短暂空白——**这是「永不空白」与「过期不展示」的取舍，见待确认项 ①**。

### 方案 2：详情页与列表完全一致（owner 点 2）

**改动 A**：`reading-engine.js` 删除 `_fetchRemainingCategories` 后台补拉（或改为仅当 `_preloadedList` 不存在时兜底，且不追加到 mergedList）。
**改动 B**：`positionText` 总数 = 透传列表长度，禁止后台改 `_total`。
**改动 C**：首页点击卡片进入详情时，`detailContext` 透传完整 `newsList`（现状已含分页，保持）。

### 方案 3：浏览历史可再读（owner 点 3）

**改动**：`recordBrowse` 成功记录历史时，**同时触发 `setNewsRetained`**（`retainedBy: 'browse'`），历史新闻 TTL 7→30 天，与收藏/分享一致。
**注意**：这会扩大 retained 集合（凡读过的都保留 30 天），库容量影响需 FS 评估（预估可控：单用户浏览量级有限，且 retained 清理周期 30 天）。
**备选**：仅当用户从历史页点进详情时触发留存（懒留存），改动更小但存在「历史列表能显示、点进去却已过期」的中间态。→ **待确认项 ②**。

### 方案 4：历史/收藏进入按来源顺序滑动 + 读毕提示（owner 点 4）

**改动 A**：`history.js` / `favorites.js` 的 `onItemTap` 改为透传来源列表：`app.globalData.detailContext = { category: 'browse' | 'favorite', list: 当前去重排序后的完整列表, source: 'history' | 'favorites' }`，URL 追加 `&source=history|favorites`。
**改动 B**：`detail.js`/`reading-engine.js` 识别 `source`：
- `source=history|favorites` → 用透传列表构建 mergedList（**禁止补拉、禁止跨分类**），按列表顺序翻页；
- 无透传（如分享卡片进入）→ 维持现有全分类合并行为（仅此场景）。
**改动 C**：边界提示（新增）：
- 最后一条上滑 → toast「**已阅读完，回到首页获取更多新闻**」；
- 第一条下滑 → toast「**已经是第一篇了**」；
- 跨分类闪烁条逻辑在单列表模式下不再触发（无跨分类）。

### 方案 5：首页翻底/翻顶拉取节奏（owner 点 5）

**改动 A**：`loadMoreNews` 每次 `pageSize = 5`（新增常量 `MORE_PAGE_SIZE = 5`），上限由「15 条硬顶」改为「**连续拉取 3 次**」计数（`_loadMoreCount`，翻底成功拉取即 +1）。
**改动 B**：toast 文案统一：
- 触发时：「**抓取更多新闻中**」（loading，800ms）；
- 拉取成功：「已加载 N 条」；
- 已无更多：「**已经到底啦**」；
- 连续 3 次后再次翻底：「**已阅读了 {newsList.length} 条新闻，建议稍后再读**」（不再拉取）。
**改动 C**：翻顶 `refreshCurrentCategory` toast 改为「**抓取更多新闻中**」（拉最新一轮当前分类，pageSize=5）。
**改动 D**：`newsList` 追加/刷新后同步侧边栏（现状已做，保持）。

## 七、验收标准

1. **列表一致性**：首页翻到底追加后，侧边栏、详情页滑动范围与列表条数**完全一致**；详情页滑动不跨分类；
2. **过期过滤**：列表/侧边栏不含任何过期新闻；过期未读新闻详情显示「新闻不存在或已过期」；
3. **历史/收藏再读**：浏览过/收藏过的新闻在 TTL 内（30 天）可从历史/收藏进入阅读；
4. **来源顺序**：从历史/收藏进入详情，滑动顺序 = 来源列表顺序；最后一条上滑 toast「已阅读完，回到首页获取更多新闻」；第一条下滑 toast「已经是第一篇了」；
5. **拉取节奏**：首页翻底 toast「抓取更多新闻中」+ 每次追加 5 条；连续 3 次后再翻底 toast「已阅读了 x 条新闻，建议稍后再读」且不再拉取；
6. **回归**：v5/v6/v7/v11/v12/v13 全部通过；首页/详情/历史/收藏/设置无报错。
