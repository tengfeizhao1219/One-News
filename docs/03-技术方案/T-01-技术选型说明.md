## 1. 框架 / 运行时

### 背景
项目自 MVP 起即为微信小程序原生开发，已积累 WXML/WXSS/JS + WXS 技术栈。当前已上线：首页卡片流、详情页同分类翻页、暗色模式、侧边栏、五层降级数据。

### 候选方案
| 方案 | 描述 |
|------|------|
| A（当前） | 微信小程序原生（WXML/WXSS/JS + WXS） |
| B | uni-app / Taro 跨端框架 |
| C | 小程序 + WebView 混合 |

### 决策：方案 A — 延续原生

### 理由
- **无跨端需求**：产品定位纯微信小程序，无支付宝/抖音/Web 版本规划。
- **WXS 手势层不可替代**：首页卡片滑动体验依赖 WXS 纯 ES5 手势（`touch.wxs`），跨端框架对 WXS 支持有限，迁移成本高且可能破坏滑动体验。
- **现有资产**：`home.js`、`detail.js`、`touch.wxs`、云函数、数据层回归套件（178 用例）均为原生代码，重写代价远超收益。
- **云开发集成**：原生 `wx.cloud` API 与 CloudBase 无缝衔接，无中间层。

### 权衡
| 获得 | 放弃 |
|------|------|
| 零迁移成本，现有资产复用 | 无法一套代码多端发布 |
| WXS 手势性能最优 | 开发体验不如现代框架（无 TypeScript/HMR） |
| 微信 API 直调无中间损耗 | 组件生态不如 Taro（但有 tdesign-miniprogram 可补） |

## 2. 云服务

### 背景
项目使用微信云开发 CloudBase：云函数（getNewsList/getNewsDetail/refreshNews）+ 云数据库（news/news_cache/sync_logs 集合）+ 环境变量管理 API Key。

### 候选方案
| 方案 | 描述 |
|------|------|
| A（当前） | 微信云开发 CloudBase |
| B | 自建后端（Node.js/Go + 独立服务器） |
| C | 第三方 BaaS（Supabase/Firebase） |

### 决策：方案 A — 延续 CloudBase

### 理由
- **原生鉴权**：`wx.cloud.callFunction` 天然携带微信用户 openid，无需自建鉴权体系。阶段二 RQ-03 云端同步预留了 `openid` 字段，CloudBase 直接可用。
- **内容安全 API 集成**：`cloud.openapi.security.msgSecCheck` 为 CloudBase 原生封装，免 access_token 管理（A-12a §RQ-10 已定）。
- **定时触发器**：`refreshNews` 的定时触发（6:00/11:00/20:00）依赖 CloudBase 定时器，自建需额外 cron 服务。
- **零运维**：无服务器/数据库运维负担，团队规模小（TL + 前后端 + 测试）。

### 权衡
| 获得 | 放弃 |
|------|------|
| 零运维、原生鉴权、安全 API 直达 | 云函数冷启动（~200ms，可接受） |
| 与小程序生态深度绑定 | 非微信平台不可用（但无此需求） |
| 环境变量安全管理 | 无法使用非 JS 运行时 |

## 3. RQ-01 跨分类衔接数据方案

### 背景
PRD §5.1 要求：详情页滑到本分类最后一条时自动衔接下一分类首条。A-12a 已对方案 A vs B 做出决策。

### 候选方案
| 方案 | 做法 | A-12a 评估 |
|------|------|-----------|
| **A（选定）** | `detailContext.list` 扩展为全分类合并有序列表（按 constants 分类顺序拼接各分类首 pageSize 条），翻页即在同一列表上移动 | 体验无缝；首屏需预拉多分类，内存 KB 级可接受 |
| B | 到达末尾时按需 `getNewsList(nextCategory)` 拉下一分类首条 | 省流量；衔接处短暂 loading |

### 决策：方案 A — 全分类预合并列表（A-12a 已定）

### 理由
- **阅读体验连贯**：无分类边界 loading，符合 PRD "沉浸式连读"目标。
- **内存可控**：5 分类 × 10 条索引 ≈ 50 条对象引用（< 5KB），小程序内存完全可承受。
- **预取策略**：进入详情时并行 `getNewsList(cat, 1, 10)` × 5，或串行合并一次调用，首屏耗时可控。
- **WXS 兼容**：合并列表在手势层仅作数据源，WXS 不感知分类上下文（满足红线 #1 #2）。

### 参数确认
- 合并顺序：`constants.js` CATEGORIES 定义顺序（top → tech → finance → sports → life）
- 读到底后若 `hasMore=true`：追加调用 `getNewsList(cat, page+1)` 扩展列表
- 边界：全部分类最后一条 → 展示"已经是最后一条"提示

### 权衡
| 获得 | 放弃 |
|------|------|
| 阅读连贯、无分类边界感 | 首屏多拉 4 个分类（可并行，总耗时 ≈ 最慢一个） |
| 实现简单（列表即游标） | 网络开销略增（约 +4 次 API 调用） |

## 4. RQ-10 内容安全 API 接入

### 背景
PRD §5.2：现有 `validator.js` 仅做字段完整性/来源白名单/垃圾词检测，未接微信内容安全 API。违规内容可致小程序下架，P0 必做。A-12a 已确定技术方案。

### 候选方案
| 方案 | 描述 |
|------|------|
| **A（选定）** | `cloud.openapi.security.msgSecCheck`（CloudBase 原生集成） |
| B | 自建服务端调用微信 `msgSecCheck`（需 access_token 管理） |
| C | 第三方内容审核 API（阿里云/腾讯云内容安全） |

### 决策：方案 A — CloudBase 原生 msgSecCheck + 保守策略兜底

### 理由
- **零鉴权成本**：`cloud.openapi.security` 为 CloudBase 原生封装，无需管理 access_token 和刷新逻辑。
- **架构位置明确**：`refreshNews` 中 `validateAndClean` 之后、`batchInsert` 之前串行接入（A-12a 已定）。
- **保守策略**：API 不可用时暂缓入库并告警，**不绕过校验**。符合 PRD AC-RQ10。
- **与 validator 分工**：`validator` 管质量/来源 → `securityCheck` 管违规，互补不合并。

### 实现参数
| 项 | 决策 |
|-----|------|
| 文本审核 | `cloud.openapi.security.msgSecCheck({ content })` |
| 图片审核 | `cloud.downloadFile(picUrl)` → `imgSecCheck`；无图跳过 |
| 批量限频 | ≤ 50 条/次，10 QPS 串行（≤ 5s），超时降级保守策略 |
| 日志 | `sync_logs` 扩展 `securityCheck: { passed, hitType, hitReason, checkedAt }` |
| 告警 | 单次命中率 > 20% 或 API 连续 3 次不可用 → ERROR 级日志 |

### 权衡
| 获得 | 放弃 |
|------|------|
| 合规底线兜住，零鉴权成本 | 内容安全 API 有 QPS 配额限制，批量时需限频 |
| 与 CloudBase 深度集成 | 不可迁移到非微信平台（无此需求） |
| 保守策略保证安全优先 | API 不可用时 news_cache 空窗，L4/L5 接住 |

## 5. RQ-03/RQ-06 存储方案

### 背景
PRD §5.4/5.7：收藏（P1）需本地持久化；阅读历史（P2）概要设计。无登录体系。A-12a 已定：本地优先 + 云端预留。

### 候选方案
| 方案 | 描述 |
|------|------|
| **A（选定）** | 本地优先（`wx.setStorageSync`）+ 云端 openid 同步预留 |
| B | 纯云端存储（需登录/授权） |
| C | 纯本地存储（永不云端同步） |

### 决策：方案 A — 本地优先 + 云端预留

### 理由
- **无登录体系**：当前无用户系统，本地存储立即可用。
- **换设备扩展**：数据结构保留 `openid` 字段（本期 null），下迭代加云函数 `syncFavorites` 即可同步。
- **容量可控**：上限 500 条（LRU 淘汰），`addedAt` 倒序。
- **与 RQ-06 共享存储层**：`favorites` 和 `readHistory` 两个独立 key，共用 `utils/localCache.js` 封装。

### 存储 schema
```js
// favorites key
wx.setStorageSync('favorites', [
  { id, title, category, categoryName, addedAt, openid: null }
])

// readHistory key（P2）
wx.setStorageSync('readHistory', [
  { id, title, category, readAt }
])
```

### 权衡
| 获得 | 放弃 |
|------|------|
| 零依赖、弱网可用 | 换设备丢失（需云端同步才解决） |
| 实现简单、即时上线 | 500 条上限（LRU 淘汰旧数据） |
| 云端预留扩展性 | 本期不实现云端同步 |

## 6. RQ-04 字体系统

### 背景
PRD §5.3：用户可调字号（3–4 档），全局生效并记忆，首入跟随系统。A-12a 已确定 CSS 变量方案。

### 候选方案
| 方案 | 描述 |
|------|------|
| **A（选定）** | CSS 变量 `--font-scale` × 4 档，与暗色模式变量共存 |
| B | 动态 `wxss` 注入（`wx.loadFontFace` 等） |
| C | 每个组件独立 `style` 绑定 |

### 决策：方案 A — CSS 变量 `--font-scale`

### 理由
- **与暗色模式统一**：`theme.json` 已有颜色 CSS 变量体系，新增 `--font-scale` 自然扩展。
- **全局生效**：`detail.wxss` / `home.wxss` 统一 `calc(原字号 * var(--font-scale))`，所有页面自动同步。
- **记忆**：`wx.setStorageSync('fontScale', x)`，启动时注入 `globalData`，各页 `onShow` 同步。
- **4 档**：标准(1) / 大(1.15) / 特大(1.3) / 超大(1.5)。

### 权衡
| 获得 | 放弃 |
|------|------|
| 与暗色模式统一、全局自动生效 | 超大字号下标题/摘要需额外截断保护 |
| 实现简单、CSS 级切换无闪烁 | 不支持无极调节（4 档固定） |

### 背景
PRD §5.5：详情页分享按钮 + 微信转发卡片（标题+摘要+封面）。A-12a 已确定封面兜底方案。

|------|------|
| **A（选定）** | `onShareAppMessage` + Canvas 客户端生成占位图兜底 |

### 理由

- **可扩展**：后续可顺带开通 `onShareTimeline`（分享到朋友圈）。

| 获得 | 放弃 |

## 11. 前端工具层 — localCache 封装（新增）

### 背景
阶段二新增收藏（RQ-03）、阅读历史（RQ-06）、离线缓存（RQ-05）三个本地存储需求。三者均依赖 `wx.setStorageSync`，但当前无统一封装，各自散落实现会导致重复代码和 TTL/LRU 策略不一致。

### 决策：新增 `utils/localCache.js` 统一封装

### 设计
```js
// utils/localCache.js
const localCache = {
  get(key)           // wx.getStorageSync(key)，未命中返回 null
  set(key, value)    // wx.setStorageSync(key, value)
  remove(key)        // wx.removeStorageSync(key)
  getWithTTL(key)    // 带 TTL 读取（超时返回 null）
  setWithTTL(key, value, ttlMs)  // 带 TTL 写入
  lruPush(key, value, maxSize)   // LRU 队列追加，超出 maxSize 淘汰最早
}

module.exports = localCache
```

### 使用方
| 模块 | Key | TTL | LRU 上限 |
|------|-----|-----|----------|
| 收藏 (RQ-03) | `favorites` | 无（持久） | 500 |
| 阅读历史 (RQ-06) | `readHistory` | 无（持久） | 200 |
| 离线缓存 (RQ-05) | `offline_news_{id}` | 24h | — |

### 权衡
| 获得 | 放弃 |
|------|------|
| 三模块共享一套封装，TTL/LRU 一致 | 增加一个工具文件（~50 行） |
| 后续扩展本地存储能力无需改业务代码 | — |
