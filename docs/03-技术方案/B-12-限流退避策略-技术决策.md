## 0. TL 结论（先看这里）

B-12 原始定义写的是「天行+聚合配额保护」，但 **v4.2 已移除天行/聚合**，当前唯一对外付费/限流风险点是**智谱 GLM-4-Flash（主力）+ DeepSeek（降级）**。故本方案重写为 **智谱/DeepSeek 配额保护**，落地 6 项策略：

1. **调用间隔**：分类间插入 `MIN_CALL_GAP_MS` 节流，尊重智谱 RPM。
2. **429 识别**：`httpsRequest` 区分限流错误 → 复用 config 已有 `API_RATE_LIMIT` 错误码。
3. **指数退避 + jitter**：限流时重试 ≤3 次，尊重 `Retry-After`。
4. **DeepSeek 预算熔断**：每日调用上限 + 熔断，防止 $5 额度被一次故障耗尽。
5. **手动触发冷却**：防用户刷新按钮与定时触发器叠加成突发。
6. **智谱调用量监控**：轻量计数 + 告警，不硬限（免费档）。

> **核心判断**：当前 `zhipuSearch` 顺序调用、无间隔、无退避、DeepSeek 无上限——一次智谱抖动就会把全部 5~7 类请求砸向 DeepSeek，数日内烧光额度。本方案以最小改动堵住该风险。

## 1. 现状核查（代码为唯一真源）

### 1.1 调用模型（zhipuSearch.js）
- `searchAllCategories()`：**顺序** `for...of` 遍历分类，每类 `await searchNewsByCategory()`。
- 每类：先 `searchWithZhipu()`（智谱）→ catch 后 `searchWithDeepSeek()`（DeepSeek）→ 再 catch 返回空。
- **无任何调用间隔**：上一类结束立即发起下一类。
- **无 429 处理**：`httpsRequest` 仅 `res.statusCode !== 200` 即 reject 为普通错误，不区分限流。
- **DeepSeek 无预算**：每次智谱失败都无上限地调用 DeepSeek。

### 1.2 已具备但未使用的资产
- `config.errorCodes.API_RATE_LIMIT = 'API_RATE_LIMIT'` —— **定义了却从未被引用**，正是为限流预留。

### 1.3 触发频率（影响配额测算）
- 代码 `config.json` 当前：**每天 3 次**（6/11/20 点）。
- ADR-002 目标 / DEP-01 部署要求：**每小时 1 次**（`0 * * * *`）。
- 若按每小时跑，LLM 调用量是 3×/日的 **8 倍**，限流/退避的必要性陡增。本文按**每小时**设计（ADR-002 权威态），并在 §5 给出两种频率的测算。

## 2. 配额风险测算

| 场景 | 智谱调用/运行 | DeepSeek 调用/运行（全失败最坏） | 日调用量（每小时×24） |
|------|:---:|:---:|:---:|
| 智谱全成功 | 5~7 | 0 | 智谱 120~168 |
| 智谱全失败→DeepSeek | 5~7 | 5~7 | 智谱 120~168 + **DeepSeek 120~168** |

- **智谱 GLM-4-Flash**：永久免费 + 2000 万 token，但有 RPM/TPM 限制（公开档约数 RPM）。顺序 5~7 次/运行若间隔过短易触 RPM。
- **DeepSeek**：注册送 $5（历史约 50 次/日感知），**额度有限**。若智谱持续故障，DeepSeek 每日 120~168 次 → 远超赠送额度 → 额度耗尽 → 全类无数据。
- **结论**：DeepSeek 必须有预算熔断；智谱必须有间隔+退避避免无谓触发降级。

## 3. 技术决策（TL 拍板）：6 项策略

### 策略 1：分类间调用间隔（防智谱 RPM）
- 新增配置 `config.rateLimit.minCallGapMs = 1500`。
- 在 `searchAllCategories()` 循环内，每类调用后 `await sleep(minCallGapMs)`（首类不睡）。
- 作用：把 5~7 次/运行的请求摊开，避免瞬时打满智谱 RPM。

### 策略 2：429 / 限流识别
- `httpsRequest` 在 `res.statusCode === 429` 时 reject `new Error('API_RATE_LIMIT')`（或带 `errorCode` 字段），不再笼统当普通错误。
- 智谱/DeepSeek 若返回限流特有 body（如智谱 `error.code: '1113'`、DeepSeek `error.type: 'rate_limit_error'`），在解析处归一为 `API_RATE_LIMIT`。
- 复用 `config.errorCodes.API_RATE_LIMIT`（消除「定义了不用」的债）。

### 策略 3：指数退避 + jitter（限流时重试）
- 对 `API_RATE_LIMIT` 错误：最多重试 `maxRetries = 3` 次。
- 退避基准 `backoff = min(maxBackoffMs, baseMs * 2^attempt)`，`baseMs = 1000`，`maxBackoffMs = 8000`。
- 叠加随机 jitter `±30%`，避免惊群。
- 若响应含 `Retry-After` 头，以该值为准（秒→毫秒）。
- 退避仅作用于**当前分类的单次引擎调用**，不跨分类累积超时。

### 策略 4：DeepSeek 预算熔断（防额度耗尽）🔴
- 新增 `system_kv` 云集合（或复用 `news_cache` meta 文档），doc id = `ratelimit:{YYYY-MM-DD}`，存 `{ deepseekCalls, zhipuCalls, updatedAt }`。
- 配置 `config.rateLimit.deepseekDailyCap = 40`（留余量，远低于 $5 额度可支撑的日调用）。
- 每次准备调用 DeepSeek 前：读当日计数，若 `deepseekCalls >= deepseekDailyCap` → **跳过 DeepSeek**，该分类标记 `engine: 'skipped_quota'`，返回空并 `console.warn`。
- 每日 0 点自然换 doc id 重置（或 count 字段按日期滚动）。
- 作用：即使智谱全天故障，DeepSeek 日耗被锁在 40 次内，保护 $5 额度不被一次事故烧光。

### 策略 5：手动触发冷却（防突发叠加）
- 在 `refreshNews/index.js` 主函数入口：读 `system_kv` 的 `lastRefreshAt`。
- 若 `now - lastRefreshAt < cooldownMs`（配置 `config.rateLimit.manualCooldownMs = 10 * 60 * 1000`）且本次为**手动触发**（event.source === 'manual'）→ 直接返回 `{ code: 0, message: '冷却中，请稍后再刷新', data: { skipped: true } }`，不跑搜索。
- 定时触发器（event.source === 'timer'）不受冷却限制。
- 作用：用户连点刷新不会与每小时定时叠加成短时突发。

### 策略 6：智谱调用量监控（不硬限）
- 每次智谱调用后 `zhipuCalls++` 写入 `system_kv`。
- `refreshNews` 返回 `data.searchStats` 已含每类 engine；建议追加 `data.quota = { zhipuCalls, deepseekCalls, deepseekCap }` 便于 PM/TL 看板观测。
- 不设置智谱硬上限（免费档），仅监控 + 告警阈值（如单日智谱 > 200 次时 warn）。

## 5. 两种触发频率下的可行性

| 频率 | 智谱日调用 | DeepSeek 最坏日调用 | 本方案是否足够 |
|------|:---:|:---:|:---:|
| 每天 3 次（config.json 现状） | 15~21 | 15~21 | ✅ 余量极大 |
| 每小时 1 次（ADR-002 目标） | 120~168 | 熔断锁 40 | ✅ 智谱免费档够，DeepSeek 被熔断保护 |

> ⚠️ **依赖项**：本方案假设 refreshNews 按 ADR-002 每小时运行。若 `config.json` 触发器仍维持 3×/日，限流压力小但 B-09「新闻时效性」与 ADR-002 目标不符——需先核对 DEP-01 是否已将触发器改为每小时（见 TL 给 PM 的核对清单）。

## 6. 验收标准

- [ ] `searchAllCategories` 分类间存在可测的 `≥ minCallGapMs` 间隔
- [ ] 模拟 429 响应时，`zhipuSearch` 触发指数退避（≤3 次）而非立即降级/抛错
- [ ] DeepSeek 当日调用达 `deepseekDailyCap` 后，后续分类跳过 DeepSeek 并返回 `skipped_quota`，不报错
- [ ] 手动触发距上次 < `manualCooldownMs` 时被拦截返回冷却提示，定时触发不受影响
- [ ] `refreshNews` 返回体含 `quota.{zhipuCalls, deepseekCalls, deepseekCap}`
- [ ] `config.errorCodes.API_RATE_LIMIT` 已被实际使用（消除死代码）
- [ ] 单测覆盖：退避次数上限、熔断跳过、冷却拦截（建议补 `test/b12-ratelimit-test.js`）
