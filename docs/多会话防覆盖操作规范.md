# 多会话防覆盖操作规范(2026-08-24 · 全员强制)

> **适用**:所有 AI 会话 + owner(微信开发者工具手动编辑)。
> **为什么**:多个会话共享同一本地目录 `C:\Users\zteng\Desktop\One News`(单副本编辑模式),
> 两个会话同时改同一文件 → **后写者静默覆盖先写者**,git 只能事后发现,无法事前拦截。
> **违反后果**:他人工作丢失、部署不一致、云端与本地副本漂移——请严格遵守。

---

## 强制规则(每次编辑必走三步)

### 第 1 步:编辑前(必做,顺序执行)

```bash
# ① 拉最新,以线上为准(多会话下这是唯一的事实基准)
git pull --rebase

# ② 看一眼有没有人正在改你要动的文件
bash scripts/file-lock.sh status

# ③ 获取文件锁(拿到锁才能编辑)
bash scripts/file-lock.sh lock <文件相对路径> <会话标识>
```

- **lock 成功** → 可以编辑
- **lock 失败(被占用)** → 输出会显示持有者——**不得硬编辑**,等其解锁或协商分工

### 第 2 步:编辑后(必做,顺序执行)

```bash
# ① 释放锁
bash scripts/file-lock.sh unlock <文件相对路径> <会话标识>

# ② 只提交自己改的文件(严禁 git add -A)
git add <改动的文件列表>
git commit -m "类型: 简述"

# ③ 推送(pre-push 门禁自动检查,通过才放行)
git push
```

### 第 3 步:异常处理

| 情况 | 做法 |
|---|---|
| 锁被占用 | 等 / 与持有者协商 / 确认无人在编辑后才 `force-unlock` |
| 发现文件被改乱 | `git diff` 对比基线;`git reflog` / `git fsck --lost-found` 找回未提交内容 |
| 无法判断归属 | 在 `intel-docs/COMMLOG.md` 广播求助,不擅自覆盖 |
| 锁过期残留 | TTL 30 分钟自动清理,无需手工处理 |

## 会话标识约定

| 编辑者 | 会话标识 |
|---|---|
| AI 会话(按角色) | `session-I` / `session-D` / `session-O` / `session-A` / `session-P` / `session-Q` / `session-K` |
| owner(微信开发者工具手动编辑) | `session-devtools` |

写锁时把标识带上,他人才能识别持有者:
```bash
bash scripts/file-lock.sh lock cloudfunctions/newsPipeline/index.js session-I
```

---

## 红线(禁止行为)

- ❌ **不 lock 就编辑**(锁被占时硬编辑 = 覆盖他人工作的根源)
- ❌ **用 `git add -A` / `git add .` 批量提交**(会把他人未提交的 WIP 一起带进 commit)
- ❌ **长时间持锁不释放**(>30 分钟自动过期,但请编辑完立即 unlock)
- ❌ **绕过 pre-push 门禁**(`--no-verify` 一律禁止;门禁 = check_intel.sh 关键逻辑/冲突标记/语法)
- ❌ **push 前不 pull**(远端有新提交时先 `pull --rebase` 合并,别直接 push 覆盖)
- ❌ **修改文件前不查看 lock status**(先避开他人正在改的文件)

## 速查卡

```bash
# 查看所有活动锁(编辑前先看)
bash scripts/file-lock.sh status

# 获取锁
bash scripts/file-lock.sh lock <文件> <会话标识>

# 释放锁
bash scripts/file-lock.sh unlock <文件> <会话标识>

# 强制解锁(仅确认无人在编辑时使用)
bash scripts/file-lock.sh force-unlock <文件>
```
