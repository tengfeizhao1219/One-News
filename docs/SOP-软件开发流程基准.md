# 软件开发流程基准（SOP）

> **版本**：v1.5 | **生效日期**：2026-07-28 | **基于项目**：一页
> **维护原则**：每个项目阶段性成果后回溯复盘，持续优化本基准
> **适用范围**：所有软件开发项目

---

## 一、流程总览

```
迭代0：需求分析     → [GATE-0] →
迭代1：UI/UX设计    → [GATE-1] →
迭代2：技术方案     → [GATE-2] →
迭代3：MVP开发      → [GATE-3] →
迭代4：完整功能     → [GATE-4] →
迭代5：测试与发布   → [GATE-5] → 上线
                                    → 项目复盘 → 更新本基准
```

**核心原则**：
1. **门禁驱动** — 每个阶段有入口/出口标准，不满足不能进下一阶段
2. **交叉评审** — 产出物的作者不能是自己的评审通过决策者
3. **测试左移** — 测试用例在需求阶段就开始编写
4. **全程可追溯** — 每个决策有记录，每次变更有影响分析
5. **持续改进** — 每个项目完成后复盘，优化本基准
6. **全局最优与举一反三** — 任何修复必须以根因为导向：先定位系统性根因再动手；修复一个问题必须扫描同类问题是否遍布其他模块，并评估对其它功能模块的连带影响；拒绝"打补丁式"局部修补，交付全局最优方案

## 二、角色与职责

| 角色 | 职责 | 关键产出 |
|------|------|----------|
| PM | 需求分析、PRD、范围管理、评审组织、发布决策 | PRD、评审纪要、发布评审 |
| 设计师 | 视觉风格、交互原型、视觉走查 | 设计规范文档、Demo、走查报告 |
| 架构师 | 技术选型、架构、数据模型、代码终审 | 技术方案、代码评审记录 |
| 开发 | 页面/组件/服务开发、代码自审、单元测试 | 代码、自测清单、单元测试 |
| QA | 测试用例、测试执行、Bug管理、测试报告 | 测试用例、测试报告、Bug记录 |

> 小团队可一人多角色，但**交叉评审规则不可违反**。

## 三、六阶段流程详解

### 迭代0：需求分析

| 节点 | 主责 | 参与 | 决策者 | 产出物 |
|------|------|------|--------|--------|
| 竞品分析 | PM | - | - | 竞品分析报告 |
| 用户画像 | PM | - | - | 用户画像文档 |
| PRD编写 | PM | 架构师 | 架构师 | PRD文档 |
| 需求评审会 | PM主讲 | 架构师+设计师+QA | 架构师 | 评审纪要 |
| 测试用例初稿 | QA | PM | PM | 测试用例初稿 |

**GATE-0 检查项**：
- [ ] PRD所有功能点有明确验收标准
- [ ] 评审纪要中所有意见已处理或记录
- [ ] 每个需求点至少1条正向+1条逆向测试用例
- [ ] 用户画像与PRD无矛盾

### 迭代1：UI/UX设计

| 节点 | 主责 | 参与 | 决策者 | 产出物 |
|------|------|------|--------|--------|
| 视觉风格+配色 | 设计师 | PM | - | 设计规范文档（Markdown） |
| 线框图+交互原型 | 设计师 | 前端 | - | 线框图文档 |
| 设计评审会 | 设计师主讲 | PM+前端+QA | PM | 评审纪要 |
| 设计走查清单 | 设计师 | - | PM | 走查清单 |
| Demo制作+确认 | 设计师 | PM+用户 | PM+用户 | 交互式Demo（HTML） |

**GATE-1 检查项**：
- [ ] 逐项对照PRD，设计覆盖所有需求
- [ ] 走查清单所有项通过
- [ ] 用户确认Demo
- [ ] 前端确认技术可实现

### 迭代2：技术方案

| 节点 | 主责 | 参与 | 决策者 | 产出物 |
|------|------|------|--------|--------|
| 技术选型+架构 | 架构师 | 前端 | - | 技术方案文档 |
| 数据模型+API设计 | 架构师 | 前端+QA | - | 数据模型+API文档 |
| 技术方案评审会 | 架构师主讲 | 前端+QA | 前端 | 评审纪要 |

**GATE-2 检查项**：
- [ ] 技术方案能支撑所有设计需求
- [ ] PRD所有字段在数据模型中有对应
- [ ] API接口定义清晰，无歧义
- [ ] 关键路径有性能评估

### 迭代3：MVP开发

| 节点 | 主责 | 参与 | 决策者 | 产出物 |
|------|------|------|--------|--------|
| 项目骨架+核心页面 | 开发 | 架构师 | - | 可运行代码 |
| 开发自测 | 开发 | - | - | 自测清单 |
| 代码评审 | 开发提交 | 架构师终审 | 架构师 | CR记录 |
| 单元测试 | 开发 | - | - | 单元测试报告 |

**GATE-3 检查项**：
- [ ] 代码评审无P0/P1问题
- [ ] Mock 回归测试全部通过（见第十三章）
- [ ] 核心逻辑单元测试覆盖率>70%
- [ ] 自测清单全部通过
- [ ] 无P0/P1未修复Bug

| 节点 | 主责 | 参与 | 决策者 | 产出物 |
|------|------|------|--------|--------|
| 完整功能开发 | 开发 | 架构师 | - | 完整代码 |

| 性能测试 | QA | 开发+架构师 | QA | 性能测试报告 |
| Bug修复+回归 | 开发 | QA验证 | QA | 回归通过 |

**GATE-4 检查项**：
- [ ] 新增代码无P0/P1问题

- [ ] 所有测试通过或有条件通过

## 六、UI设计产出标准（双轨制）

### 6.1 设计原则

UI设计阶段采用**双轨产出**：交互式 Demo（给人看效果）+ 设计规范文档（给开发对照、评审引用、AI协作）。

```
UI设计阶段产出
├── 设计规范文档（Markdown）     ← 开发对照 / 评审引用 / AI协作
│   ├── 色彩 token（精确到hex）
│   ├── 字体规范（精确到rpx/weight/line-height）
│   ├── 间距系统（精确到rpx）
│   ├── 组件规格（每个组件的完整属性）
│   └── 动效参数（时长/曲线/阈值）
│
└── 交互式 Demo（HTML）          ← 视觉预览 / 用户确认
    └── 多项目通过 Tab 切换
```

### 6.2 交互式 Demo（HTML）

**用途**：视觉预览、交互验证、用户确认

**规范**：
- 统一入口：所有项目共用一个 HTML 文件，通过顶部 Tab 切换不同项目
- 文件路径：`demo/ui-showcase.html`（全局唯一，跨项目复用）
- 每个项目一个 Tab，Tab 内展示该项目的所有页面/视图
- 可交互：手势/点击/滑动等核心交互需可操作
- 响应式：模拟手机尺寸（375×812 或按实际设计稿）
- 每个UI元素旁标注引用编号（如"§3.2"），关联到设计规范文档对应章节

### 6.3 设计规范文档（Markdown）

**用途**：开发对照、评审引用、AI协作、变更追溯

**规范**：
- 每个项目独立一份，路径：`docs/iteration-1/设计规范文档.md`
- 所有数值精确到具体单位（hex色值、rpx尺寸、ms时长）
- 通过Git版本管理，变更可 diff 追踪
- AI可读取解析，用于代码评审时对照

**文档结构模板**：

```markdown
# [项目名] 设计规范文档

## 一、色彩系统
| token名称 | 色值 | 用途 |
|-----------|------|------|
| --bg-page | #F5F3F0 | 页面背景 |
| --text-primary | #1C1C1E | 主文字 |
（暗色模式另列一套）

## 二、字体系统
| 用途 | 字号 | 字重 | 行高 | 字体族 |
|------|------|------|------|--------|
| 卡片标题 | 52rpx | 700 | 1.35 | PingFang SC |
| 正文 | 32rpx | 400 | 1.9 | Songti SC |

## 三、间距系统
| 用途 | 值 |
|------|----|
| 页面边距 | 64rpx |
| 卡片内边距 | 80rpx |

## 四、组件规格
### 4.1 [组件名]
| 属性 | 值 |
|------|----|
| 宽度 | xxx |
| 高度 | xxx |
| 背景 | xxx |
（每个组件一个子章节）

## 五、动效参数
| 动效 | 时长 | 曲线 | 触发阈值 |
|------|------|------|----------|
| 卡片切换 | 380ms | cubic-bezier(0.22,0.61,0.36,1) | 50px |

## 六、效果预览
> 完整交互效果见 Demo：ui-showcase.html → Tab: [项目名]
```

### 6.4 双轨关联规则

- Demo 中每个UI元素标注引用编号（如"§3.2"），指向设计规范文档对应章节
- 设计规范文档末尾注明"效果见 Demo Tab: [项目名]"
- 评审时以文档为基准引用，Demo 用于直观验证
- 代码评审时，AI读取设计规范文档，逐项对照代码实现

## 七、测试用例管理标准

### 7.1 格式要求

所有项目的测试用例**统一使用 Excel（.xlsx）格式**编写和管理，便于筛选、排序、统计和协作。

### 7.2 Excel 列结构

| 列 | 字段名 | 说明 | 示例 |
|----|--------|------|------|
| A | 用例ID | 模块缩写-编号 | TC-HOME-001 |
| B | 模块 | 所属模块名 | 首页卡片流 |
| C | 优先级 | P0/P1/P2/P3 | P0 |
| D | 用例类型 | 正向/逆向/边界/异常 | 正向 |
| E | 前置条件 | 执行前需满足的条件 | 已加载新闻数据 |
| F | 测试步骤 | 1. xxx 2. xxx（换行分隔） | 1.打开小程序 2.上滑 |
| G | 预期结果 | 预期表现 | 切换到下一条，动画流畅 |
| H | 实际结果 | 执行时填写 | |
| I | 状态 | 待执行/通过/失败/阻塞/跳过 | 通过 |
| J | Bug编号 | 关联Bug ID（如有） | BUG-001 |
| K | 执行轮次 | 第1轮/回归 | 第1轮 |
| L | 执行人 | 测试执行人 | QA |
| M | 执行日期 | YYYY-MM-DD | 2026-07-28 |
| N | 备注 | 补充说明 | |

### 7.3 格式规范

- **标题行**：加粗、浅灰背景、冻结首行
- **优先级列**：P0红色、P1橙色、P2黄色、P3灰色文字
- **状态列**：通过绿色、失败红色、待执行灰色、阻塞橙色
- **筛选**：所有列开启自动筛选
- **Sheet 分页**：按模块分 Sheet

### 7.4 文件命名

```
测试用例_[项目名]_v[版本号].xlsx
例：测试用例_一页_v1.0.xlsx
```

### 7.5 版本管理

- 每次用例变更需更新文件版本号
- 旧版本保留在 `docs/testcases/archive/` 目录
- 终版用例需在 GATE-5 前冻结，冻结后不再修改

## 八、Bug分级标准

| 级别 | 定义 | 处理时效 |
|------|------|----------|
| P0 | 阻断性：崩溃、白屏、核心功能不可用 | 必须修复才能发布 |
| P1 | 严重：主要功能异常、数据错误 | 必须修复才能发布 |
| P2 | 一般：次要功能问题、体验不佳 | 发布前尽量修复 |
| P3 | 轻微：文案、样式小问题 | 可延期修复 |

## 十三、Mock 回归测试强制流程

### 13.1 原则

**每次代码变更后，必须先通过 Mock 数据的完整回归测试（SIT），确认所有已有功能不受影响后，方可进入集成测试或部署环节。**

这是测试左移的具体落地——用 mock 数据模拟真实场景，在不依赖外部 API 的情况下完成端到端验证。

### 13.2 适用场景

| 场景 | 说明 |
|------|------|
| 每次代码提交 | 开发自测：切换 `USE_MOCK = true`，验证核心流程 |
| 功能迭代完成 | QA 全量回归：逐条执行回归用例 |

## 十四、AI 新闻缓存架构规范

### 14.1 背景

对于依赖外部新闻/内容 API 的应用，传统方案面临三个痛点：
- **费用**：第三方 API 按调用次数收费
- **延迟**：外部 API 响应 500-2000ms
- **稳定性**：API 可能限流、宕机、变更

本规范提出一种**零费用、零延迟、零外部依赖**的替代方案：用 WorkBuddy 的 WebSearch + WebFetch 能力实时搜索新闻，生成本地 JSON 缓存作为主数据源。

### 14.2 架构设计

```
┌─────────────────────────────────────────────┐
│              数据流架构 v2.0                 │
├─────────────────────────────────────────────┤
│                                             │
│  WorkBuddy AI（手动触发 / 定期）             │
│  ├─ WebSearch 5个分类                       │
│  ├─ WebFetch 提取详情                       │
│  └─ 输出 mock/ai-news-cache.js              │
│                  ↓                          │
│  build-ai-cache.js（构建脚本）               │
│  └─ 转换为 cloudfunctions/common/aiNewsData  │
│                  ↓                          │
│  ┌─────────────────────────────────────┐    │
│  │  小程序前端 (utils/request.js)       │    │
│  │  ├─ Mock 模式 → 直接读 ai-news-cache │    │
│  │  └─ 生产模式 → 云函数               │    │
│  └──────────────┬──────────────────────┘    │
│                  ↓                          │
│  ┌─────────────────────────────────────┐    │
│  │  云函数 getNewsList / searchNews     │    │
│  │  ├─ 第1层：内存缓存                  │    │
│  │  ├─ 第2层：AI 缓存 (aiNewsService)   │    │
│  │  ├─ 第3层：云数据库缓存              │    │
│  │  └─ 第4层：外部 API（可选降级）      │    │
│  └─────────────────────────────────────┘    │
│                                             │
└─────────────────────────────────────────────┘
```

### 14.3 关键模块

| 模块 | 路径 | 职责 |
|------|------|------|
| AI 缓存数据源 | `mock/ai-news-cache.js` | WorkBuddy 生成的新闻 JSON 数组 |
| AI 新闻服务 | `cloudfunctions/common/aiNewsService.js` | 查询、搜索、分页、统计 |
| 缓存数据文件 | `cloudfunctions/common/aiNewsData.js` | 云函数可加载的数据副本 |
| 构建脚本 | `scripts/build-ai-cache.js` | 将 mock 缓存转换为云函数格式 |
| 请求层 | `utils/request.js` | 双模式：Mock 读本地 / 生产走云函数 |
| 模拟器 | `mock/simulator.js` | 支持 normal/error/empty/slow 四种场景 |

### 14.4 AI 缓存更新流程

```
用户告诉 WorkBuddy:
  "搜索最新新闻更新 AI 缓存"
       ↓
WorkBuddy 执行:
  1. WebSearch 5个分类（推荐/科技/体育/国际/生活）
  2. WebFetch 提取关键内容
  3. 生成符合数据模型的 JSON 数组
  4. 写入 mock/ai-news-cache.js
  5. 运行 node scripts/build-ai-cache.js
  6. 运行 node test/mock-regression.js（验证）
       ↓
完成 — 缓存版本号更新，可部署
```

### 14.5 数据模型要求

每条新闻必须包含以下字段：

| 字段 | 类型 | 说明 | 示例 |
|------|------|------|------|
| id | string | 唯一标识，格式: `ai_{cat}_{序号}` | `ai_tech_001` |
| title | string | 新闻标题 | `WAIC 2026世界人工智能大会闭幕` |
| summary | string | 摘要（100-500字） | `2026世界人工智能大会...` |
| category | string | 分类ID | `tech` |
| categoryName | string | 分类中文名 | `科技` |
| source | string | 来源媒体 | `新华社` |
| publishTime | string | ISO 8601 时间 | `2026-07-28T08:30:00Z` |

### 14.6 外部 API 降级策略

AI 缓存是**主数据源**，外部 API 仅作为**可选备用**：

```
AI 缓存有数据 → 直接返回（零延迟）
    ↓ 无数据
云数据库缓存 → 返回（上次 API 调用的缓存）
    ↓ 无缓存
天行数据 API → 返回（需 API Key）
    ↓ 失败
聚合数据 API → 返回（需 API Key）
    ↓ 失败
过期缓存 → 返回（带 warning 标记）
    ↓ 无任何数据
返回错误（ALL_DOWN）
```

### 14.7 优势与限制

**优势**：
- 零费用 — 无需购买任何第三方 API
- 零延迟 — 本地数据即时响应
- 零外部依赖 — 即使外部 API 全部宕机也不影响
- 内容可控 — 可筛选、编辑、分类
- 可审计 — 所有数据版本受 Git 管理

**限制**：
- 非实时 — 数据更新依赖手动触发 WorkBuddy 搜索
- 条数有限 — 每次搜索约 30-50 条，适合轻量级应用
- 内容时效 — 建议每天更新一次，保持新闻新鲜度

### 14.8 何时使用此模式

| 适用场景 | 不适用场景 |
|----------|------------|
| 新闻阅读类应用（日更即可） | 实时行情/股价 |
| 内容聚合/信息流 | 即时通讯 |
| 知识库/百科类 | 需要秒级更新的数据 |
| 个人博客/作品集 | 用户生成内容（UGC） |

## 十五、全局最优与举一反三原则（强制）

> **来源**：一页项目迭代中，侧边栏卡死与首页乱码问题被"打补丁式"修复反复加重，用户明确要求：
> "不能为了解决问题而解决问题……需要举一反三是不是其他地方会有类似问题，且需要全局考虑对其他功能模块会不会产生额外的影响，我要的是一个最优且能全局解决问题的方案。"
> 本条为**所有软件开发类工程的永久规则**。

### 15.1 四条铁律

| # | 铁律 | 含义 | 反例（禁止） |
|---|------|------|------|
| 1 | **根因导向** | 先定位系统性根因，再动手修复；禁止在没搞清楚"为什么"前就改代码 | 看到乱码就删 emoji、看到卡顿就加 catchtouchmove |
| 2 | **举一反三** | 修复一个问题时，必须全局扫描同类问题是否存在于其他模块/文件 | 只改出问题的那一行，不管别处同样写法 |
| 3 | **全局影响评估** | 改动前评估对其它功能模块的连带影响，避免按下葫芦浮起瓢 | 修复 A 却让 B 回归，且无回归测试 |
| 4 | **最优方案** | 交付架构级、一次到位的方案，而非症状级补丁 | 用 `opacity:0` 假装隐藏、用死代码假装防护 |

### 15.2 执行流程（每次修复必走）

```
1. 复现   → 稳定复现问题，记录真实现象（区分"真因"与"表象"）
2. 根因   → 用排除法定位到系统性根因（编码？架构？生命周期？）
3. 扫描   → 全局 grep/扫描同类写法，列出所有受影响文件
4. 评估   → 分析改动对其它模块的连带影响，识别风险点
5. 方案   → 设计架构级最优方案（宁可多花时间，不要打补丁）
6. 验证   → 改完后跑全量回归测试 + 新增针对性回归用例锁定不变量
```

### 15.3 源码编码铁律（UTF-8 统一）

微信开发者工具要求所有源码为 **UTF-8**。任何以 GBK/GB2312 等编码保存的源文件都会在真机/工具中表现为中文乱码。

- **写入/保存**：所有含中文的源文件必须以 UTF-8 写入（编辑器、生成脚本、AI 工具均须显式指定 UTF-8）
- **提交前自检**：用 `file -i <file>` 或 Python `open(f).read().decode('utf-8')` 校验，发现 `iso-8859-1`/`GBK` 立即转码
- **转码命令**：`iconv -f GBK -t UTF-8` 或 Python `open(f,'w',encoding='utf-8').write(open(f,encoding='gb18030').read())`
- **禁止**：用 emoji/ASCII 字符替换中文来"绕过"乱码——这是掩盖症状，根因是编码，不是字符

### 15.4 已知反模式清单（命中即重构）

| 反模式 | 后果 | 正确做法 |
|--------|------|----------|
| 触摸手势绑在根视图（如 `.page`）上 | 全屏拦截触摸，干扰面板/按钮/滚动 | 只绑在实际交互区（如 `.card-stage`） |
| 祖先元素用 `catchtouchmove` 包住 `scroll-view` | `preventDefault` 禁掉原生滚动→列表卡死 | 不拦截；或滚动区独立、不套 catchtouchmove |
| 用 `opacity:0`/`visibility:hidden` "隐藏"需禁用的层 | 元素仍在布局中、仍参与命中测试 | 用 `display:none` 彻底移除 |
| WXS/JS 中定义防护接口但从未调用 | 死代码，伪防护，问题照旧 | 要么真正接线，要么删除 |
| 同类写法散落多处只改其一 | 别处同样 bug 复发 | 全局扫描后统一改 |
| 用 ASCII 替换中文掩盖乱码 | 乱码更严重、可读性崩坏 | 修复文件编码为 UTF-8 |

### 15.5 与现有流程的关联

- **变更管理（第九章）**：本条铁律并入"影响分析"步骤——变更前必须完成举一反三扫描与全局影响评估
- **GATE 检查（各阶段）**：新增否决项——"修复未定位根因 / 未扫描同类问题 / 无回归测试锁定" 一律不得通过
- **Mock 回归测试（第十三章）**：每次修复后必须新增针对性回归用例（如架构不变量测试），防止同类问题复发
