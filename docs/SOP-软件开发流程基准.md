# 软件开发流程基准（SOP）

> **版本**：v1.2 | **生效日期**：2026-07-28 | **基于项目**：一页
> **维护原则**：每个项目阶段性成果后回溯复盘，持续优化本基准
> **适用范围**：所有软件开发项目

---

## 一、流程总览

```
迭代0：需求分析     → [GATE-0] →
迭代1：UI/UX设计    → [GATE-1] →
迭代2：技术方案     → [GATE-2] →
迭代3：MVP开发      → [GATE-3] →
迭代4：完整功能     → [GATE-4] →
迭代5：测试与发布   → [GATE-5] → 上线
                                    → 项目复盘 → 更新本基准
```

**核心原则**：
1. **门禁驱动** — 每个阶段有入口/出口标准，不满足不能进下一阶段
2. **交叉评审** — 产出物的作者不能是自己的评审通过决策者
3. **测试左移** — 测试用例在需求阶段就开始编写
4. **全程可追溯** — 每个决策有记录，每次变更有影响分析
5. **持续改进** — 每个项目完成后复盘，优化本基准

---

## 二、角色与职责

| 角色 | 职责 | 关键产出 |
|------|------|----------|
| PM | 需求分析、PRD、范围管理、评审组织、发布决策 | PRD、评审纪要、发布评审 |
| 设计师 | 视觉风格、交互原型、视觉走查 | 设计规范文档、Demo、走查报告 |
| 架构师 | 技术选型、架构、数据模型、代码终审 | 技术方案、代码评审记录 |
| 开发 | 页面/组件/服务开发、代码自审、单元测试 | 代码、自测清单、单元测试 |
| QA | 测试用例、测试执行、Bug管理、测试报告 | 测试用例、测试报告、Bug记录 |

> 小团队可一人多角色，但**交叉评审规则不可违反**。

## 三、六阶段流程详解

### 迭代0：需求分析

| 节点 | 主责 | 参与 | 决策者 | 产出物 |
|------|------|------|--------|--------|
| 竞品分析 | PM | - | - | 竞品分析报告 |
| 用户画像 | PM | - | - | 用户画像文档 |
| PRD编写 | PM | 架构师 | 架构师 | PRD文档 |
| 需求评审会 | PM主讲 | 架构师+设计师+QA | 架构师 | 评审纪要 |
| 测试用例初稿 | QA | PM | PM | 测试用例初稿 |

**GATE-0 检查项**：
- [ ] PRD所有功能点有明确验收标准
- [ ] 评审纪要中所有意见已处理或记录
- [ ] 每个需求点至少1条正向+1条逆向测试用例
- [ ] 用户画像与PRD无矛盾

### 迭代1：UI/UX设计

| 节点 | 主责 | 参与 | 决策者 | 产出物 |
|------|------|------|--------|--------|
| 视觉风格+配色 | 设计师 | PM | - | 设计规范文档（Markdown） |
| 线框图+交互原型 | 设计师 | 前端 | - | 线框图文档 |
| 设计评审会 | 设计师主讲 | PM+前端+QA | PM | 评审纪要 |
| 设计走查清单 | 设计师 | - | PM | 走查清单 |
| Demo制作+确认 | 设计师 | PM+用户 | PM+用户 | 交互式Demo（HTML） |

**GATE-1 检查项**：
- [ ] 逐项对照PRD，设计覆盖所有需求
- [ ] 走查清单所有项通过
- [ ] 用户确认Demo
- [ ] 前端确认技术可实现

### 迭代2：技术方案

| 节点 | 主责 | 参与 | 决策者 | 产出物 |
|------|------|------|--------|--------|
| 技术选型+架构 | 架构师 | 前端 | - | 技术方案文档 |
| 数据模型+API设计 | 架构师 | 前端+QA | - | 数据模型+API文档 |
| 技术方案评审会 | 架构师主讲 | 前端+QA | 前端 | 评审纪要 |

**GATE-2 检查项**：
- [ ] 技术方案能支撑所有设计需求
- [ ] PRD所有字段在数据模型中有对应
- [ ] API接口定义清晰，无歧义
- [ ] 关键路径有性能评估

### 迭代3：MVP开发

| 节点 | 主责 | 参与 | 决策者 | 产出物 |
|------|------|------|--------|--------|
| 项目骨架+核心页面 | 开发 | 架构师 | - | 可运行代码 |
| 开发自测 | 开发 | - | - | 自测清单 |
| 代码评审 | 开发提交 | 架构师终审 | 架构师 | CR记录 |
| 单元测试 | 开发 | - | - | 单元测试报告 |
| Bug修复+回归 | 开发 | QA验证 | QA | Bug修复确认 |

**GATE-3 检查项**：
- [ ] 代码评审无P0/P1问题
- [ ] 核心逻辑单元测试覆盖率>70%
- [ ] 自测清单全部通过
- [ ] 无P0/P1未修复Bug

### 迭代4：完整功能开发

| 节点 | 主责 | 参与 | 决策者 | 产出物 |
|------|------|------|--------|--------|
| 完整功能开发 | 开发 | 架构师 | - | 完整代码 |
| 代码评审 | 开发提交 | 架构师 | 架构师 | CR记录 |
| 集成测试 | QA | 开发 | QA | 集成测试报告 |
| 性能测试 | QA | 开发+架构师 | QA | 性能测试报告 |
| Bug修复+回归 | 开发 | QA验证 | QA | 回归通过 |

**GATE-4 检查项**：
- [ ] 新增代码无P0/P1问题
- [ ] 所有模块联调通过
- [ ] 性能指标达标
- [ ] 无P0/P1，P2<3个

### 迭代5：测试与发布

| 节点 | 主责 | 参与 | 决策者 | 产出物 |
|------|------|------|--------|--------|
| 测试用例终版 | QA | PM+开发 | PM | 用例终版（Excel） |
| 全量功能测试 | QA | - | - | 测试执行记录 |
| 兼容性测试 | QA | - | - | 兼容性结果 |
| 视觉走查 | 设计师 | - | PM | 走查报告 |
| 测试报告评审 | QA主讲 | 全员 | PM | 测试报告 |
| 发布评审(Go/No-Go) | PM主持 | 全员 | 全员 | 发布评审纪要 |

**GATE-5 检查项**：
- [ ] 所有测试通过或有条件通过
- [ ] 视觉走查无重大偏差
- [ ] 发布清单所有项确认
- [ ] 全员一致同意发布

## 六、UI设计产出标准（双轨制）

### 6.1 设计原则

UI设计阶段采用**双轨产出**：交互式 Demo（给人看效果）+ 设计规范文档（给开发对照、评审引用、AI协作）。

```
UI设计阶段产出
├── 设计规范文档（Markdown）     ← 开发对照 / 评审引用 / AI协作
│   ├── 色彩 token（精确到hex）
│   ├── 字体规范（精确到rpx/weight/line-height）
│   ├── 间距系统（精确到rpx）
│   ├── 组件规格（每个组件的完整属性）
│   └── 动效参数（时长/曲线/阈值）
│
└── 交互式 Demo（HTML）          ← 视觉预览 / 用户确认
    └── 多项目通过 Tab 切换
```

### 6.2 交互式 Demo（HTML）

**用途**：视觉预览、交互验证、用户确认

**规范**：
- 统一入口：所有项目共用一个 HTML 文件，通过顶部 Tab 切换不同项目
- 文件路径：`demo/ui-showcase.html`（全局唯一，跨项目复用）
- 每个项目一个 Tab，Tab 内展示该项目的所有页面/视图
- 可交互：手势/点击/滑动等核心交互需可操作
- 响应式：模拟手机尺寸（375×812 或按实际设计稿）
- 每个UI元素旁标注引用编号（如"§3.2"），关联到设计规范文档对应章节

### 6.3 设计规范文档（Markdown）

**用途**：开发对照、评审引用、AI协作、变更追溯

**规范**：
- 每个项目独立一份，路径：`docs/iteration-1/设计规范文档.md`
- 所有数值精确到具体单位（hex色值、rpx尺寸、ms时长）
- 通过Git版本管理，变更可 diff 追踪
- AI可读取解析，用于代码评审时对照

**文档结构模板**：

```markdown
# [项目名] 设计规范文档

## 一、色彩系统
| token名称 | 色值 | 用途 |
|-----------|------|------|
| --bg-page | #F5F3F0 | 页面背景 |
| --text-primary | #1C1C1E | 主文字 |
（暗色模式另列一套）

## 二、字体系统
| 用途 | 字号 | 字重 | 行高 | 字体族 |
|------|------|------|------|--------|
| 卡片标题 | 52rpx | 700 | 1.35 | PingFang SC |
| 正文 | 32rpx | 400 | 1.9 | Songti SC |

## 三、间距系统
| 用途 | 值 |
|------|----|
| 页面边距 | 64rpx |
| 卡片内边距 | 80rpx |

## 四、组件规格
### 4.1 [组件名]
| 属性 | 值 |
|------|----|
| 宽度 | xxx |
| 高度 | xxx |
| 背景 | xxx |
（每个组件一个子章节）

## 五、动效参数
| 动效 | 时长 | 曲线 | 触发阈值 |
|------|------|------|----------|
| 卡片切换 | 380ms | cubic-bezier(0.22,0.61,0.36,1) | 50px |

## 六、效果预览
> 完整交互效果见 Demo：ui-showcase.html → Tab: [项目名]
```

### 6.4 双轨关联规则

- Demo 中每个UI元素标注引用编号（如"§3.2"），指向设计规范文档对应章节
- 设计规范文档末尾注明"效果见 Demo Tab: [项目名]"
- 评审时以文档为基准引用，Demo 用于直观验证
- 代码评审时，AI读取设计规范文档，逐项对照代码实现

## 七、测试用例管理标准

### 7.1 格式要求

所有项目的测试用例**统一使用 Excel（.xlsx）格式**编写和管理，便于筛选、排序、统计和协作。

### 7.2 Excel 列结构

| 列 | 字段名 | 说明 | 示例 |
|----|--------|------|------|
| A | 用例ID | 模块缩写-编号 | TC-HOME-001 |
| B | 模块 | 所属模块名 | 首页卡片流 |
| C | 优先级 | P0/P1/P2/P3 | P0 |
| D | 用例类型 | 正向/逆向/边界/异常 | 正向 |
| E | 前置条件 | 执行前需满足的条件 | 已加载新闻数据 |
| F | 测试步骤 | 1. xxx 2. xxx（换行分隔） | 1.打开小程序 2.上滑 |
| G | 预期结果 | 预期表现 | 切换到下一条，动画流畅 |
| H | 实际结果 | 执行时填写 | |
| I | 状态 | 待执行/通过/失败/阻塞/跳过 | 通过 |
| J | Bug编号 | 关联Bug ID（如有） | BUG-001 |
| K | 执行轮次 | 第1轮/回归 | 第1轮 |
| L | 执行人 | 测试执行人 | QA |
| M | 执行日期 | YYYY-MM-DD | 2026-07-28 |
| N | 备注 | 补充说明 | |

### 7.3 格式规范

- **标题行**：加粗、浅灰背景、冻结首行
- **优先级列**：P0红色、P1橙色、P2黄色、P3灰色文字
- **状态列**：通过绿色、失败红色、待执行灰色、阻塞橙色
- **筛选**：所有列开启自动筛选
- **Sheet 分页**：按模块分 Sheet

### 7.4 文件命名

```
测试用例_[项目名]_v[版本号].xlsx
例：测试用例_一页_v1.0.xlsx
```

### 7.5 版本管理

- 每次用例变更需更新文件版本号
- 旧版本保留在 `docs/testcases/archive/` 目录
- 终版用例需在 GATE-5 前冻结，冻结后不再修改

## 八、Bug分级标准

| 级别 | 定义 | 处理时效 |
|------|------|----------|
| P0 | 阻断性：崩溃、白屏、核心功能不可用 | 必须修复才能发布 |
| P1 | 严重：主要功能异常、数据错误 | 必须修复才能发布 |
| P2 | 一般：次要功能问题、体验不佳 | 发布前尽量修复 |
| P3 | 轻微：文案、样式小问题 | 可延期修复 |

## 九、变更管理流程

```
变更申请 → 影响分析 → 变更评审 → 变更执行 → 变更验证 → 基线更新
```

每次变更需记录：
- 变更内容（变更前/变更后）
- 影响范围（文档/代码/测试/进度）
- 评审结论（批准/驳回）
- 验证结果

## 十一、项目复盘机制

### 11.1 复盘时机

| 时机 | 类型 | 目的 |
|------|------|------|
| 每个GATE通过时 | 阶段微复盘 | 发现本阶段流程问题，即时调整 |
| 项目上线后 | 项目全量复盘 | 全面总结，更新流程基准 |
| 季度回顾 | 跨项目复盘 | 对比多个项目，发现系统性问题 |

### 11.2 复盘内容

```markdown
# [项目名] 项目复盘报告

## 一、项目概况
- 项目名称：
- 周期：
- 团队：

## 二、流程执行情况
| 阶段 | 计划工时 | 实际工时 | 偏差 | 原因 |
|------|----------|----------|------|------|

## 三、质量数据
- Bug总数及分布：
- 评审发现问题数：
- 测试用例覆盖率：
- 性能指标达标率：

## 四、流程问题与改进
| # | 问题描述 | 根因 | 改进措施 | 是否更新基准 |
|---|----------|------|----------|------------|

## 五、经验沉淀
- 做得好的（Keep）：
- 做得不好的（Problem）：
- 下次尝试的（Try）：

## 六、流程基准更新建议
- [ ] 建议新增的流程节点：
- [ ] 建议修改的检查项：
- [ ] 建议删除的不合理项：
```

### 11.3 基准更新流程

```
项目复盘 → 提出基准更新建议 → 全员评审 → 更新SOP版本号 → 通知所有成员
```

版本号规则：v主版本.次版本（v1.0 → v1.1 小优化，v1.0 → v2.0 大调整）
