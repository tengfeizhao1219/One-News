## 一、测试目标

验证 `getNewsList` 云函数的五层降级链路（L1→L2→L3→L4→L5→ALL_DOWN）在各级故障时按预期下沉，确保：

1. **降级顺序正确**：L1 失败 → L2 → L3 → L4 → L5，不跳级
2. **每一层独立有效**：单独故障时正确下沉到下一层
3. **多级连锁故障**：L1+L2+L3 同时故障时正确到达 L4/L5
4. **终极兜底 ALL_DOWN**：全链路故障时返回正确错误码
5. **meta.source 正确**：每层返回对应的 source 标记
6. **数据不交叉污染**：降级返回的数据与来源一致

---

## 二、测试架构

### 2.1 故障注入方法

| 层 | 故障注入方式 | 操作人 | 恢复方式 |
|----|-------------|--------|---------|
| **L1 天行** | 临时修改 `TIAN_API_KEY` 为无效值（如 `FAULT_INJECTED`） | 后端开发 | 恢复原 Key |
| **L2 内存** | 云函数实例冷启动（新请求触发新实例）/ 或手动 `cache.clear()` | 后端开发 | 下一次 L1 成功自动回填 |
| **L3 云库** | 临时将 `news_cache` 集合的 TTL 设为过期（`cacheExpire < now`） | 后端开发 | `refreshNews` 重新写入 |
| **L4 聚合** | 临时删除/无效化 `JUHE_API_KEY` | 后端开发 | 恢复原 Key |
| **L5 AI** | 临时清空 AI 静态缓存文件 / 无效化 `DASHSCOPE_API_KEY` | 后端开发 | 恢复缓存文件 |

### 2.2 验证手段

每次请求检查 `meta.source` 字段：

| meta.source | 含义 | 预期触发条件 |
|-------------|------|-------------|
| `tian_api` | L1 天行实时 | 正常请求（无故障） |
| `memory_cache` | L2 内存缓存 | L1 故障 + L2 命中 |
| `db_cache` | L3 云数据库缓存 | L1+L2 故障 + L3 命中 |
| `juhe_fallback` | L4 聚合降级 | L1+L2+L3 故障 + L4 成功 |
| `ai_cache` | L5 AI 静态缓存 | L1+L2+L3+L4 故障 + L5 命中 |
| — (code:-1) | ALL_DOWN | 全部故障 |

## 四、测试执行流程

```
准备阶段（后端开发配合）
├── 1. 确认所有环境变量正常 → 执行 DG-01（基线）
├── 2. 先触发一次 L1 成功 → L2 缓存写入
│
故障注入阶段（逐级）
├── 3. 注入 L1 故障 → 执行 DG-02（L2 验证）
├── 4. 清空 L2 + L1 故障 → 执行 DG-03（L3 验证）
├── 5. L1+L2+L3 故障 → 执行 DG-04（L4 验证）
├── 6. L1+L2+L3+L4 故障 → 执行 DG-05（L5 验证）
├── 7. 全链路故障 → 执行 DG-06（ALL_DOWN 验证）
│
特殊场景
├── 8. L4 可选 → 执行 DG-07
├── 9. 分类隔离 → 执行 DG-08
├── 10. 恢复验证 → 执行 DG-09
├── 11. 分页一致性 → 执行 DG-10
│
清理
└── 12. 恢复所有环境变量 → 执行 DG-01（确认恢复）
```
