# 发版机制与版本管理规范

> **制定者**：项目经理  
> **生效日期**：2026-08-02  
> **适用范围**：前端（微信小程序）、后端（云函数）所有发版动作  
> **强制要求**：**每次发版必须带版本号 + Release Note（发版日志），缺一不可。**

---

## 一、版本号规范（语义化版本 SemVer）

格式：`MAJOR.MINOR.PATCH`（例：`1.0.0`）

| 位 | 名称 | 递增条件 | 示例 |
|----|------|----------|------|
| MAJOR | 主版本 | 不兼容变更 / 重大架构重构 / 产品定位变化 | `1.0.0` → `2.0.0` |
| MINOR | 次版本 | 向下兼容的功能新增 | `1.0.0` → `1.1.0` |
| PATCH | 修订版本 | 向下兼容的 Bug 修复 / 小调整 | `1.0.0` → `1.0.1` |

**当前基线版本**：`V1.0.0`（首版，见 `docs/06-上线复盘/Q-06.3-小程序审核准备.md`）

**递增示例**：
- 修复 BUG-008 → `1.0.1`
- 新增 RQ-15 侧边分类滚轮 → `1.1.0`
- 云函数引擎大重构 → `2.0.0`

> ⚠️ **禁止**使用日期、构建号、随意字符串作为版本号（如 `20260802`、`build123`）。

---

## 二、发版分类

| 类型 | 说明 | 版本变化 |
|------|------|----------|
| 全量发版 | 前后端同步上线 | 前端 + 后端各自递增版本 |
| 前端热修 | 仅前端小程序修复 | 前端 `PATCH +1` |
| 后端热修 | 仅云函数修复 | 后端 `PATCH +1` |
| 灰度发版 | 5% → 20% → 100% | 版本不变，备注灰度比例 |

---

## 三、发版流程

### 🟦 前端发版流程（微信小程序）

```
1. 确认 main 分支最新（git pull）
2. 更新版本号（改 CHANGELOG.md + 提交审核时填版本号/描述）
3. 微信开发者工具 → 上传（填版本号 + 版本描述）
4. 微信公众平台 → 提交审核（版本描述复用 Release Note 摘要）
5. 审核通过后 → 全量发布 / 灰度发布
6. 打 git tag：git tag -a v1.0.1 -m "前端热修：BUG-008"
7. git push origin --tags
8. 更新 CHANGELOG.md + TASK_BOARD 广播 + COMMLOG 记录
```

### 🟩 后端发版流程（云函数）

```
1. 确认 main 分支最新（git pull）
2. 微信云开发控制台 → 上传部署对应云函数（getNewsList/refreshNews/getNewsDetail）
3. 配置环境变量（如 API Key 变更）
4. 验证云函数日志无报错
5. 更新版本号（CHANGELOG.md）
6. 打 git tag：git tag -a v1.0.1-backend -m "后端：xxx 修复"
7. git push origin --tags
8. 更新 CHANGELOG.md + TASK_BOARD 广播 + COMMLOG 记录
```

## 四、每次发版必须项（Checklist）

- [ ] 版本号已按 SemVer 递增
- [ ] 写了 Release Note（用下方模板）
- [ ] 更新了 `CHANGELOG.md`
- [ ] 打了 git tag（`vX.Y.Z` 或 `vX.Y.Z-backend`）
- [ ] `git push origin --tags` 已执行
- [ ] TASK_BOARD 广播区发布了发版通知
- [ ] COMMLOG 记录了发版动作
- [ ] 确认回滚方案可用（见 `docs/06-上线复盘/` 回滚预案）

> 🔴 **红线**：没有 Release Note 和版本号的发版，视为无效发版，PM 有权打回。

---

## 五、Release Note 模板

发布时请复制以下模板，填写后放入 `CHANGELOG.md` 对应版本条目：

```markdown
## [v1.0.1] - 2026-08-02

**发版类型**：前端热修 / 后端热修 / 全量发版 / 灰度
**发版人**：<角色名>
**版本号**：v1.0.1

### 变更内容
- **新增**：（无 / 列出新增功能）
- **优化**：（无 / 列出优化项）
- **修复**：BUG-008 侧边栏滑动竞态修复

### 影响范围
<受影响页面 / 云函数 / 用户群>

### 验证方式
<如何在真机/测试环境验证>

### 回滚方案
<如何回滚：git revert / 云函数版本回退 / 小程序回退上一版本>
```

---

## 六、CHANGELOG 规范

- 文件位置：仓库根目录 `CHANGELOG.md`
- 格式：遵循 [Keep a Changelog](https://keepachangelog.com/) 标准
- 条目顺序：新版本在上，旧版本在下
- 分类：`新增` / `优化` / `修复` / `移除`

---

## 七、git tag 规范

| 场景 | tag 格式 | 示例 |
|------|----------|------|
| 前端发版 | `vMAJOR.MINOR.PATCH` | `v1.0.1` |
| 后端发版 | `vMAJOR.MINOR.PATCH-backend` | `v1.0.1-backend` |
| 全量发版 | `vMAJOR.MINOR.PATCH` | `v1.1.0` |

```bash
# 打标签
git tag -a v1.0.1 -m "前端热修：BUG-008 修复"
# 推送标签
git push origin --tags
```

---

## 八、给前后端的特别说明

### 前端开发
- 版本号在**微信开发者工具上传时填写**，同时更新 `CHANGELOG.md`
- 小程序审核描述 = Release Note 摘要，不要写"修复若干 bug"这种废话

### 后端开发
- 云函数没有"版本号"界面，用 git tag 管理版本
- 每次上传部署后必须打 tag，否则无法回滚

---

## 九、违规处理

| 违规 | 处理 |
|------|------|
| 发版无版本号 | PM 打回，补齐后重新发 |
| 发版无 Release Note | PM 打回 |
| 漏打 git tag | 补打，并在 COMMLOG 说明 |
| 未更新 CHANGELOG | 补齐 |
