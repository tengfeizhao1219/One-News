# 任务交接流转机制（权威文档）

> **定位**：本文件为「一页 One-News」项目任务流转的**唯一权威定义**。所有角色会话（8 人）在执行任务时，均以本文档为准则。
> **读者**：产品经理、交互设计师、视觉设计师、技术负责人、前端开发、后端开发、测试工程师、项目经理。
> **前置阅读**：`ROLE_CARDS.md`（身份卡）→ `CONTEXT.md`（项目速览）→ 本文档（怎么干活）。

---

## 一、核心概念

### 1.1 三个核心文件，三种用途

| 文件 | 用途 | 谁维护 |
|------|------|--------|
| `TASK_BOARD.md` | **任务中枢**：所有任务的唯一管理看板。计划内（R/D/T/B/Q/L）+ 临时（A-xx）双池统一。 | 全员认领，项目经理维护结构 |
| `RELAY.md` | **跟踪表**：计划内任务线性交接全景视图，不阻塞执行。用于看清"谁在何时接谁的交付物"。 | 仅项目经理 |
| `COMMLOG.md` | **交接记录**：每次有产出物变更时追加一行交付/即席记录。 | 谁干活谁记录 |

### 1.2 两种任务来源

| 类型 | 编号 | 含义 | 举例 |
|------|------|------|------|
| **计划内** | R-/D-/T-/B-/Q-/L- | 6 阶段流水线预定义任务 | R-01 用户调研、B-02 前端开发 |
| **临时新增** | A-xx | 过程中冒出的需求/bug/决策项 | A-01 产品自查、新增 Bug 修复 |

### 1.3 两种执行模式

| 模式 | 触发方式 | 流程 | 产出物要求 |
|------|----------|------|------------|
| **拉式认领**（主线） | 用户说「接棒/继续/该你/开始阶段X」→ 看板认领 | 认领→干活→交付→建交接任务→PM 关口 | commit+push+COMMLOG |
| **即席/直连** | 用户对该角色说具体诉求（问需求、改接口、看文件…） | 直接处理 | 纯问答直接答；动产出物才 commit+push+COMMLOG；不更新 TASK_BOARD/RELAY |

## 二、拉式认领全流程（主线任务的标准路径）

### 2.1 流程图

```
git pull → 读 TASK_BOARD → 筛选我的任务 → 认领 → 干活 → 交付 → 建交接任务 → PM 关口 → 下一阶段
```

### 2.2 认领步骤（每个角色）

```
第 1 步：确认工作区文件是最新的（如需同步，让 GM 执行「同步」）
第 2 步：打开 TASK_BOARD.md
第 3 步：筛选条件：角色 = 我 且 状态 = 📋 或 (⏳ 且依赖已 ✅) 且 🔴 优先
第 4 步：认领 — 状态 📋→🔄，在「认领人」列填自己的会话名
第 5 步：开始干活
```

> ⚠️ **优先级规则**：始终先认领 🔴 任务，再 🟡，最后 🟢。🔴 = 交接依赖 / 当前焦点。
> ⚠️ **零 git 操作**：各角色不执行任何 git 命令（不 pull、不 commit、不 push）。git 操作由 GM 统一代理。

### 2.3 交付步骤（任务完成时）

```
第 1 步：对照任务完成标准逐条自查
第 2 步：状态 🔄 → ✅
第 3 步：动了产出物 → 写入 `.git-staging/<role>.ready` 标记（含 role/timestamp/summary/files）
第 4 步：在 COMMLOG.md 追加一行交付记录（时间戳 + 会话标识 + 完成内容 + 变更文件 + 📤 待 GM 提交）
第 5 步：告知用户"任务 [ID] 已完成，已写入 staging 标记待 GM 提交"
```

> ⚠️ **Git 禁令**：各角色**禁止**执行 `git add/commit/push/merge/rebase`，只能 `git pull`。Git 管理专家（GM）是唯一有权执行 git 写操作的角色。产出物由 GM 统一提交。

### 2.4 创建交接任务（关键，不可省略）⚠️ 2026-07-31 增强

**交接类任务**（即：你的产出是别人的输入）完成时，必须做：

```
第 1 步：检查 TASK_BOARD.md，找到依赖你的下游任务
第 2 步：将下游任务状态 ⏳ → 📋（激活），确认其优先级为 🔴
第 3 步：若下游任务尚不存在，新建一行（填 ID/任务/角色/优先级/依赖），状态 📋
第 4 步：⚠️ 写交接说明（不可省略，见下方模板）
第 5 步：告知用户："已为 [下一角色] 创建/激活任务 [任务ID]，请其认领"
```

**⚠️ 第 4 步交接说明模板（2026-07-31 新增）**：

激活下游任务时，**必须在 COMMLOG.md 或广播区**写清楚以下内容。**不允许只留一句"请认领"让下游猜**：

```markdown
## 🔗 交接：[上游任务ID] → [下游任务ID] | 上游：[上游角色] → 下游：[下游角色]

### 我交付了什么
- [产出物1]：路径 + 一句话说明
- [产出物2]：路径 + 一句话说明

### 下游需要做什么（具体，不要模糊）
- [ ] 具体动作1（例如：基于 docs/03-技术方案/阅读模式-技术方案.md 实现 pages/detail/reading-engine.js）
- [ ] 具体动作2
- [ ] 具体动作3

### 关键注意事项
- ⚠️ [坑1]：[具体说明，例如 "WXS 必须纯 ES5，不能用 try/catch/箭头函数"]
- ⚠️ [坑2]：[具体说明]
- 📎 参考文件：[路径]（如果有）

### 有问题找谁
- 上游：[角色名]（[具体问题领域]）
- 决策：[角色名]（[具体决策范围]）
```

**反面示例（❌ 禁止）**：
```
已激活 B-01，请前端认领。
```

**正面示例（✅ 要求）**：
```
已激活 B-01 跨分类阅读引擎，请前端认领。
交付物：docs/03-技术方案/阅读模式-技术方案.md（7 子任务拆分）
下游要做：
  1. 实现 reading-engine.js，支持上滑加载下一分类新闻
  2. 返回定位兼容（home.js → detail.js 状态回传）
  3. 正文拆分 + 空 content 兜底
注意：WXS 纯 ES5；touch.wxs 不要 return false；scroll-view 用 flex:1+min-height:0
参考：docs/02-产品设计/D-02-交互原型.md、pages/detail/detail.js（当前基础版）
上游：技术负责人（技术方案问题）→ 产品经理（交互逻辑问题）
```

**非交接类任务**（纯自查、文档归档等，无下游依赖）无需此步。

## 三、PM 关口检查（方案 A，保留）

### 3.1 什么是关口检查

每个阶段的所有任务全部 ✅ 后，**不是自动流入下一阶段**。必须由**项目经理**做一次关口检查：

```
[执行角色] 完成本阶段全部任务 → [项目经理] 关口检查（核对完成标准）→ 通过则开放下一阶段 🔴 任务；不通过则回退
```

### 3.2 关口检查清单（项目经理执行）

| 检查项 | 内容 |
|--------|------|
| 产出物完整性 | 本阶段所有文档/代码/测试产物是否已提交推送？ |
| 完成标准达标 | 每个任务的完成标准（checklist）是否全部满足？ |
| 交接任务就绪 | 下游阶段的 🔴 任务是否已创建并状态为 ⏳？ |
| 阻塞项清零 | TASK_BOARD 阻塞项表中是否有本阶段未解决的 🚫？ |
| 遗留问题登记 | 若有暂不处理的遗留项，是否已在 TASK_BOARD 或 COMMLOG 中记录？ |

### 3.3 关口通过后的操作

```
第 1 步：将下游阶段第一个任务的依赖 ⏳ → 📋（开放认领）
第 2 步：在 COMMLOG.md 追加关口检查记录
第 3 步：告知用户："[阶段X] 关口检查通过，[阶段X+1] 任务已开放，请 [下一角色] 认领"
```

### 3.4 关口不通过

```
第 1 步：在 TASK_BOARD.md 阻塞项表中记录阻塞原因 + 谁来解决
第 2 步：将问题任务标记为 🚫
第 3 步：告知用户："[阶段X] 关口检查未通过，原因：[xxx]，请 [对应角色] 修复后重新提关"
```

## 四、3 分支意图识别（角色收到消息时第一反应）

角色会话收到用户消息后，**必须先判意图，再行动**：

| 用户说了什么 | 角色判定 | 走哪条线 |
|--------------|----------|----------|
| 「接棒 / 继续 / 该你 / 开始阶段X …」且当前阶段任务属于我 | **主线触发** | **拉式认领**（见第二章） |
| 「接棒 / 继续 …」但当前阶段任务不属于我 | **误用棒触发** | **两步不可省**（见 4.1） |
| 对该角色的具体诉求（问需求、改接口、看文件…） | **即席请求** | **即席/直连**（见 4.2） |
| 超出该角色权限 | **越权** | 标记阻塞/上报，不自行决定 |

### 4.1 误用棒触发 — 必须的两步（⚠️ 高频错误点）

过去常犯的错误：角色只拒绝了就结束。**正确做法是两步都做**：

```
第 1 步：明确提示
  "当前应由 [RELAY 跟踪表指向的角色] 处理 [阶段X] 任务，我是 [我的角色]，
   请用 [正确角色] 会话认领。"

第 2 步：立即转入即席模式（不能只拒绝就结束）
  "不过如果你有需要我 [我的角色] 处理的即席任务（问答/小改/看文件/评审…），
   请直接说，我会在权限范围内处理并轻量交付（commit+push+COMMLOG），不碰跟踪表。"
```

### 4.2 即席/直连模式规则

- 权限不变，按 ROLE_CARDS.md 的身份卡执行
- 纯问答：直接回答，无需 git 操作
- 动了产出物：`git commit + push` + 在 COMMLOG.md 追加即席记录
- **不更新** TASK_BOARD.md、RELAY.md（即席不碰主线）
- 若即席任务确认该进主线：由**项目经理**登记进 TASK_BOARD（Backlog A-xx）

## 五、异常处理

### 5.1 回退（发现上一棒产出有问题）

```
第 1 步：不覆盖上一棒工作
第 2 步：在 TASK_BOARD.md 标记对应任务为 🚫
第 3 步：在阻塞项表写明问题（ID / 阻塞原因 / 谁来解决 / 记录时间）
第 4 步：告知用户："[阶段X] 产出有问题：[具体问题]，请 [原角色] 修复"
第 5 步：项目经理在 COMMLOG 记录回退事件
```

### 5.2 并行任务冲突（多人同时改公共文件）

```
第 1 步：改公共文件前先 git pull
第 2 步：若 push 被拒（non-fast-forward）→ git pull --rebase → 解决冲突 → 再 push
第 3 步：冲突无法自行解决 → 在阻塞项表登记，通知项目经理协调
```

### 5.3 依赖阻塞（上游未完成导致我无法启动）

```
第 1 步：确认 TASK_BOARD 中依赖任务的真实状态（git pull 后检查）
第 2 步：若依赖确实未完成 → 保持 ⏳，不强行开工
第 3 步：在 COMMLOG 记录："[任务ID] 等待 [依赖任务ID] 完成，暂不启动"
第 4 步：告知用户当前阻塞情况
```

## 六、并行推进规则

### 6.1 同阶段多人并行

| 场景 | 规则 |
|------|------|
| 阶段二：D-02 交互设计 与 D-03 视觉设计 | 串行（D-03 依赖 D-02），不可并行 |
| 阶段四：B-02 前端 与 B-03 后端 | 可并行（各自 feature 分支），都 ✅ 后 TL 做 B-05 代码评审 |
| 阶段五：Q-02 功能测试 与 Q-04 Bug 跟踪 | 可并行（测试执行 + PM 跟踪同步进行） |

### 6.2 并行开发时的 Git 规则

```
前端：git checkout -b feature/xxx-fe
后端：git checkout -b feature/xxx-be
→ 各自开发 → 各自 push → TL 合并时解决冲突
```

## 七、角色权限与决策权（速查）

> ⚠️ **【2026-08-03 重要区分】「决策权」与「操作权」分开**：
> - **决策权**：决定"做什么/怎么做"的拍板权，按下方表格归属不变。
> - **操作权（复核 + commit + push）**：**所有角色均可对文档类产出物做复核、修改、提交、推送**，不再限于归属角色。详见 `Git推送操作手册-各角色通用.md` §0。

### 7.1 决策权（拍板权，归属不变）

| 决策类型 | 谁说了算 |
|----------|----------|
| 做什么功能、做成什么样 | 产品经理 |
| 技术怎么实现 | 技术负责人 |
| 什么时候交付、能不能上线 | 项目经理 |
| 人力怎么分配、谁干什么 | 项目经理 |
| 质量过不过关 | 测试工程师 |
| 视觉规范、设计还原度 | 视觉设计师 |
| 交互流程、用户体验 | 交互设计师 |

### 7.2 操作权（复核 + commit + push，全员开放）

| 操作类型 | 谁有权 | 说明 |
|----------|--------|------|
| 文档复核（review） | ✅ 所有角色 | PRD / 需求池 / 设计文档 / 技术方案 / 测试报告均可被任意角色复核、提意见或修订 |
| 文档 commit + push | ✅ 所有角色 | 改完文档直接 `git commit + push origin main`，无需 PM 中转 |
| 代码 commit + push | 🔧 对应开发角色 | `cloudfunctions/` `pages/` `components/` 仍由开发角色提交，避免误改 |
| 公共跟踪文件改动 | ✅ 所有角色（先 pull） | `TASK_BOARD.md` `RELAY.md` `COMMLOG.md` 改动前必须 `git pull`，push 前 `git pull --rebase` |

## 八、Git 操作规范（所有角色通用）

### 8.1 日常操作

```bash
# 开工前
git pull origin main

# 改代码（需分支隔离时）
git checkout -b feature/<功能名>

# 交付
git add <变更文件>
git commit -m "<简短描述>"
git push origin <分支名>  # 或直接 push origin main（文档类）
```

### 8.2 公共文件修改（TASK_BOARD / RELAY / COMMLOG / CONTEXT）

```bash
git pull origin main    # 先拉最新
# 编辑文件
git add <文件>
git commit -m "<描述>"
git pull --rebase origin main  # push 前再拉一次，防冲突
git push origin main
```

### 8.3 分支规范

| 分支类型 | 命名格式 | 示例 |
|----------|----------|------|
| 功能开发 | `feature/<功能名>` | `feature/reading-mode` |
| Bug 修复 | `fix/<问题简述>` | `fix/sidebar-freeze` |
| 文档 | 直接 main（无需分支） | — |

> **【2026-08-03 权限开放】文档类改动（PRD / 需求池 / 设计 / 技术方案 / 测试报告）任何角色均可直接 `git commit + push origin main`**，无需经产品经理中转或开分支。详见 §7.2 操作权表。
