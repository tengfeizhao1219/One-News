# news_cache 复合索引检查清单（对应优化项 P0）

> 适用：云函数 `getNewsList`（列表/首页高频请求）
> 目标：消除「同一次列表请求静默翻倍 DB 读」的配额黑洞，直接缓解 `-501003` 的数据库读写请求配额

## 为什么必须有这个索引

`getNewsList` 的排序是：

```
.orderBy('finalScore', 'desc').orderBy('createdAt', 'desc')
```

这依赖 `news_cache` 集合上存在**组合索引 `(finalScore, createdAt)`（均降序）**。

- ✅ 索引存在：一次 `.get()` 即可完成排序 + 分页，每次列表 = **1 次 DB 读**。
- ❌ 索引缺失 / 异常：链式 `orderBy` 查询抛错 → 触发 R9 兜底，改用单字段 `createdAt` 再查一次。
  即**同一次列表请求 = 2 次 DB 读**，且排序精度下降。
  这是 `-501003`（数据库读写请求超额）最容易被忽略的隐形放大源——代码完全能跑，只是配额悄悄翻倍。

## 检查步骤（云开发控制台）

1. 打开「微信开发者工具 → 云开发控制台 → 数据库 → `news_cache` 集合 → 索引管理」。
2. 确认存在一条组合索引，字段顺序为：
   - 字段 1：`finalScore`，排序 **降序（DESC）**
   - 字段 2：`createdAt`，排序 **降序（DESC）**
   - 唯一/非唯一：非唯一即可
3. 若不存在 → 点击「新建索引」按上述字段与顺序创建（单字段索引不够，必须是组合索引）。
4. 创建后等索引进入「就绪」状态再观察。

> 也可在「云开发控制台 → 运营分析 → 数据库读写」对比：索引缺失时列表请求数约为实际列表次数的 2 倍。

## 代码侧已做的兜底（无需操作）

- `cloudfunctions/getNewsList/index.js` 的 `queryCache` 在组合索引排序失败时，会：
  - **首次**失败时打一条醒目的 `console.error`，提示「复合索引缺失/异常，需 (finalScore desc, createdAt desc)」并指向本清单；
  - 之后仅 `console.warn`，避免日志刷屏。
- 监控建议：在云函数日志里搜 `[⚠ 复合索引缺失/异常]`，一旦命中即优先确认索引。

## 备注

- 此索引为**控制台操作**，无法由代码自动创建；本清单供部署/排障时人工核对。
- `news_cache_backup` 集合只用单字段 `createdAt` 排序，无需复合索引，不受影响。
