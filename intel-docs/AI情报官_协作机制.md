# AI 情报官 · 多角色协作机制（v1.0）

> 本机制**改编自 One News 项目的多会话协作框架**（源文档：`One News · 协作机制`，Notion 父页 `3b66b5eb…`），并结合本项目的「100% AI 实现 + 主控(O)派生子 Agent」模型做了适配。
> 核心理念不变：**文件即通信**——所有角色通过 git 仓库 + 约定文件交换信息，不靠会议、不靠催进度。

---

## 一、团队角色映射

One News 用 4–5 个固定角色（PM/PD/FS/FE/PJM）。本项目沿用其「一个角色 = 一个固定身份、全程复用」原则，映射到我们已定义的 7 角色：

| 本项目角色 | 身份 | 对应 One News 角色 | 职责 |
|---|---|---|---|
| **O 主控** Orchestrator | 项目总控 + 编排 | PJM→PM | 拆解任务、派发子 Agent、关口检查、最终决策 |
| **I 基础设施** Infra | 技术负责人 | FS | 云函数骨架、`intel_*` 集合、定时触发器、部署 |
| **A 适配器** Adapter ×N | 数据源接入 | FS | 25 源差异化抓取（RSS/API/官网/公众号） |
| **P 处理** Process | LLM 阅读引擎 | FS | SOP 五步、关联生成、上手试试调研 |
| **D 推送UI** Delivery | 前端/UI 全栈 | FE/PD | 小程序页面、UI 规范、UI/UX 验收 |
| **Q 校验** QA | 质量把关 | PM(质量) | 交叉校验、一致性、红线审计 |
| **K 文档** Knowledge | 文档与知识 | PM(规划) | 需求/调研/设计/导航索引/本机制文档 |

> **与 One News 的关键差异**：One News 是「多个独立会话各持一角色」；本项目是「**O 主控这一个会话持有全局，按需用子 Agent 临时扮演 I/A/P/D/Q/K 角色**」。子 Agent 通过读取本机制文件 + 约定文件获得身份，交付物写回约定文件，由 O 汇总。等效于 One News 的多会话，但调度更集中、上下文更连贯。

## 三、Git 纪律（全员直连 GitHub）

> 所有角色对自己的职责范围内文件**直接** `pull / add / commit / push`，无需经他人代提交。

1. **改前先拉**：`git pull --rebase`（或带 DNS 修复，见下）。
2. **改后立即提交**：`git add <本职责文件> && git commit -m "类型: 简述" && git push`。
3. **小步快推**：不在本地堆积大量改动；一次逻辑单元一次提交。
4. **GitHub DNS 修复**（沙箱偶发 `github.com` 被解析到 `198.18.0.x` 导致 TLS 失败）：
   ```bash
   # 方案A：强制真实 IP 解析
   git -c http.curloptResolve=github.com:443:140.82.113.4 pull --rebase
   # 方案B：/etc/hosts 写入 140.82.113.4 github.com codeload.github.com api.github.com
   ```
   > 注：本沙箱已通过 `/etc/hosts` 修复，`git clone/push github.com` 已验证可用。

## 四、任务流转（认领 → 交付 → 下一棒）

1. **认领前先核对归属**：看 `RELAY.md` 确认当前阶段任务是否属于自己 → 去 `TASK_BOARD.md` 认领。
2. **状态机**：📋 待认领 → 🔄 进行中（填认领人）→ ✅ 完成（为下一角色建/激活任务）→ 🚫 阻塞（+原因）；失败/中断 → 🔁 重试中（附上次失败原因）或 ⛔ 放弃（附理由）。
3. **交付交接包**（完成交接类任务时填）：做了什么 / 产出物清单 / 给下一棒的提醒。
4. **3 分支意图识别**（收到指令时先判）：
   - **主线**：「接棒/继续/该你」且 RELAY 显示当前阶段属于我 → 认领 🔴 任务。
   - **误用棒**：说接棒但 RELAY 显示不是我 → ① 提示正确角色 ② 立即转即席（两步不可省）。
   - **即席/直连**：对其他角色直接提诉求（问答、小改、临时需求）→ 权限内处理、轻量交付、不碰跟踪表；纯问答直接答。

## 五、关口检查（Gate Check）

阶段级任务全 ✅ 后，由 **O（主控）** 做关口检查：通过才开放下一阶段任务；不通过则回退并标记 🚫 + 阻塞项说明。关口记录追加到 TASK_BOARD.md。

**质量门禁（关口检查前置，硬性，v2 新增）**：
1. 先跑 `python3 scripts/check.py intel-docs` 做约定文件一致性审计（退出码 0 才可过关口）。
2. 有自动化测试/lint/类型检查时，关口前必须跑通，结果写进关口记录。
3. 涉及部署的改动：交付包必须含「生效验证」证据（日志/接口实测），不接受"部署成功"作为完成（教训：LEARNINGS 首条）。

阶段级任务全 ✅ 后，由 **O（主控）** 做关口检查，通过才开放下一阶段 🔴 任务；不通过则回退并标记 🚫 + 阻塞项说明。

## 六、设计交付精度 + UI/UX 验收闭环（适配 D 角色）

沿用 One News 的「PD 是 UI/UX 质量最终权威」原则，映射到本项目的 **D 角色**：

1. **设计交付物**（D 产出标准）：① 1:1 可交互 HTML 原型（如 `AI情报官_UI_Demo.html`）② 精确规格设计文档（`AI情报官_UI规范_v1.md`，含 theme.json token 对照）③ 图标/手势规范。
2. **UI/UX 验收闭环**：`D 开发完成 → O 对照规范逐项走查 → 合格 ✅ / 不合格 🐛 提 Bug → D 修复 → 复验`。
3. **Bug 提单格式**：`🐛[页面/组件] 元素｜实际：X｜期望：Y｜引用：规范 §X.X｜优先级：P0/P1/P2`。
4. **不可自行推断**（I/A/P/D 侧）：❌ 不得自行改色值/透明度/圆角/间距/字重；❌ 不得自行替换图标；❌ 不得省略状态覆盖（loading/empty/error）。✅ 遇技术限制先 @O 确认替代方案。
5. **硬约束（本项目特有）**：UI 100% 复用 One News `theme.json`，**禁止新增 hex 色值**；前端改动必须标记 `INTEL-BRIDGE` 且可整体摘除。

## 七、与「100% AI + 子 Agent」模型的适配

- **O 主控**在本会话持有全局；需要并行推进时，用**子 Agent**临时扮演 I/A/P/D/Q/K，子 Agent 启动时读取 `ROLE_CARDS.md` + `CONTEXT.md` 获得身份。
- 子 Agent 的「交付」= 写回约定文件（`TASK_BOARD` 状态、`COMMLOG` 记录、`docs/` 产出物），O 汇总后做关口检查。
- 子 Agent 等效于 One News 的「独立角色会话」，但共享 O 的上下文，减少交接损耗。
- 用户（owner）仅在关键决策点拍板、在需凭证处（如 Notion token、GitHub 仓库目标）给料。

## 九（v2 新增）、教训库与决策日志

## 十（v2 新增）、DoD 完成定义（任务标 ✅ 前逐条核对）

## 十一（v2 新增）、检查点快照与归档

- **检查点快照**：每阶段关口通过时打 git tag（`git tag phase-N-done && git push --tags`）；阶段内失败需回退时 `git checkout <tag>` 恢复，不重跑。
- **COMMLOG 压缩轮转**：超 30 条或跨月时，旧条目压成「决策摘要」归档到 docs/06-上线复盘/，主 COMMLOG 只留存活信息。
- **CONTEXT/ROLE_CARDS 分层**：主文件只放高频不变规则，细节拆子文件按需加载（渐进披露，控制新会话读文件成本）。
